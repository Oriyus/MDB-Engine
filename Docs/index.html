Engine

The runtime: rendering, scenes, physics, audio, animation, navigation, save games and the systems both apps share.

Overview & architecture

MDB Engine is a C++20 game engine for Windows using OpenGL 4.5 (core profile, direct state access). The engine is a static library, Engine, used by two apps:

  • MDBEditor — the editor (folder Editor/).
  • Game — the standalone player with no editor (folder Game/).

Application runs the main loop and calls the virtual hooks OnStart, OnUpdate(dt), OnImGui and OnShutdown. Each app defines Engine::CreateApplication().

Shared runtime

  • SceneRenderer renders a scene through a camera into a texture (the editor shows it in the Viewport, the game draws it full window).
  • GameSession owns physics, audio, prefabs, scripts and navigation, steps them in order, and is also the campaign (save slots, level changes).
  • ResourceLibrary maps resource names ("cube", "model:Models/Fox.glb") to loaded meshes and textures.

One frame of play

  1. Pending loads, level changes and restarts are applied (GameSession::ApplyPending).
  2. Scene::OnUpdate: Spin, Orbit, animation, particles.
  3. Animation events, then Lua on_update, then queued events.emit events.
  4. Physics step (fixed 60 Hz, interpolated), then collision and trigger callbacks.
  5. Audio follows its entities; the scene is rendered.

Building & running

CMake with the Visual Studio 2026 generator. Dependencies download automatically (FetchContent).

cmake -S . -B build -G "Visual Studio 18 2026" -Wno-dev
cmake --build build --config Debug
.\build\bin\Debug\MDBEditor.exe [--project folder]              # the editor (the last project, else Examples)
.\build\bin\Debug\Game.exe [--project folder] [--scene x.json]   # the game (default: Examples)
cmake --build build --config Release --target package_game   # build/dist/Release: the Examples game
cmake --build build --config Release --target package_editor # build/dist/MDB Engine: the editor, ready to zip
  • Sharing the editor. package_editor makes a folder that runs on any PC without building: MDBEditor.exe, Player/Game.exe (a prebuilt Release player), EngineAssets, the Examples project, these docs and a README.txt. When EngineAssets/Shaders is next to the editor's exe, it uses that folder and the Examples beside it instead of the source tree, and File › Build Game copies Player/Game.exe instead of compiling. Recipients need the Microsoft Visual C++ Redistributable (x64), like players of a built game.
  • After adding or deleting a source file, run the configure line again (engine sources are collected with a glob; editor sources are listed in Editor/CMakeLists.txt).
  • Shaders are read at run time: F5 reloads them without rebuilding.
  • In Visual Studio, F5 starts the editor (it is the startup project).

Dependencies: GLFW, glad, GLM, spdlog, EnTT, Dear ImGui (docking), ImGuizmo, assimp, nlohmann/json, stb_image, Jolt Physics, Lua 5.4, sol2, miniaudio.

Entities & components

Scenes use an ECS (EnTT). An Entity is a thin handle with Add<T>, Get<T>, Has<T> and Remove<T>. Every entity has a name (Tag), a Transform and a stable 64-bit ID.

ComponentPurpose
TransformPosition, rotation (Euler, radians) and scale, relative to the parent
Mesh RendererGeometry, colour, metallic/roughness, emissive, textures, alpha mode, opacity, shadows, Static flag
Point Light / Directional LightLights (the first sun and up to 4 point lights are used)
Rigid BodyPhysics body: type, shape, size, centre, mass, friction, bounciness, trigger
ColliderAn extra shape for the nearest ancestor body (compound colliders)
ScriptA Lua file in Assets/Scripts
CameraGame camera (FOV, near, far, primary)
Audio SourceA looping or one-shot sound that follows the entity
AnimatorSkeletal animation: clip, speed, layers, events, root motion, IK
Particle EmitterCPU particles with presets (Fire, Smoke, Sparks, Magic, Dust, Embers)
Spin / OrbitSimple motion helpers
PrefabLink to a prefab file and node
Parent / IDHierarchy links (by ID, never by handle)
Engine::Entity e = scene.CreateEntity("Crate");
e.Get<TransformComponent>().Position = glm::vec3(2, 0, 1);
auto& mr = e.Add<MeshRendererComponent>();
mr.Geometry = resources.FindGeometry("cube");
e.Add<RigidBodyComponent>().Type = BodyType::Static;
Adding a new component type means updating Components.h, the snapshot code in Scene, the JSON functions in Scene/EntityJson.cpp, and the editor's Inspector.

Transforms & hierarchy

A child stores its parent's ID (ParentComponent) and its transform is local to the parent. Everything spatial (rendering, physics, audio, cameras, the gizmo) works in world space.

  • GetWorldMatrix, SetWorldMatrix / Position / Rotation, SetParent(child, parent, keepWorld) (refuses loops), GetChildren.
  • Destroying an entity destroys its children; duplicating copies the whole subtree with new IDs.
  • Static and kinematic bodies follow their parent; dynamic bodies simulate in world space.
Rotations are stored as Euler angles. Convert a quaternion back with Scene::EulerFromQuat, never glm::eulerAngles (it is unstable near gimbal lock and made cameras shake).

Scene files

Scenes are JSON files in Assets/Scenes. Entities store their name, ID, parent, transform and components; resources are stored by name and resolved on load.

Resource nameMeaning
"cube", "sphere", "plane", "capsule", "cylinder", "cone"Built-in meshes (capsule 1×2, cylinder 1×1, cone 1 wide × 1 tall)
"model:Models/Fox.glb"Any model file (loaded once, on demand)
"checker", "texture:Textures/fence.png"Built-in or any image texture

A settings block holds the sky/environment, ambient, post-processing, AO, bloom, shadows, gravity and the editor camera. Every field is optional, so older files load fine. Unmodified prefab instances are stored as links plus overrides.

                  "meshRenderer": { "geometry": "cube", "color": [0.7, 0.45, 0.25] },
                  "rigidBody": { "type": "static", "shape": "box" } } ],
  "settings": { "physics": { "gravity": 9.81 } } }

Grass and flowers (Foliage)

A Foliage component (Create > Grass, or Add Component > Foliage) covers an area of the entity's X/Z plane with grass and flower clumps. The clumps are generated from the settings and the Seed, so scene files store only the settings. They are drawn GPU-instanced, about one draw per 8 m chunk in view, and lit by the same shader as everything else: sun shadows, lights, sky light and fog of war all fall on them.

SettingWhat it does
Size, Density, SeedThe area (metres, centred on the entity), clumps per m², and which random layout. New seed picks another.
Avoid static objectsNo grass where Static meshes meet the ground: walls, floors, posts, trunks, props. Grass still grows under fence rails and branches. Moving those objects scatters the grass again.
Height, Height variation, WidthClump size; flowers stand a little taller.
Root / Tip / Dry color, Dry patches, FlowersBlades shade from root to tip; dry patches turn the tips to the dry colour; Flowers is the share of flower clumps.
Wind strength, speed, directionGusts roll across the field along the direction (0° blows towards +X, 90° towards +Z), and every clump flutters a little.
Interaction, RecoveryHow far things bend the grass when they move through it, and how many seconds it takes to stand up again (leaving trails).
Draw distanceThe grass thins out smoothly over the second half of it.

What presses the grass: every dynamic or kinematic rigid body (not triggers) near it, sized by its collider, and foliage.push from scripts. Clicks go through the grass to whatever is under it. The village demo has 11,600 clumps (about 790,000 triangles), which cost about 0.7 ms a frame in a Debug build.

Grass receives shadows but casts none. It stands on the entity's flat plane (it does not follow terrain).

Wind (trees)

Any Mesh Renderer can sway in the wind: set its Wind (0 = still, 1 = a tree). The higher a point is in the mesh, the more it moves, so trunks stay planted while crowns bend with the gusts and the leaves flutter. Shadows sway with it. The wind itself is in Scene Settings > Wind (direction, speed, strength) and is saved with the level. It blows in Edit mode too, so you see it while building.

The gusts roll across the level the same way as on the grass, so trees and the grass under them move together. Grass fields keep their own wind settings (Foliage component). Scripts: self.mesh.wind = 0.8 or add_mesh{ ..., wind = 1 }.

A swaying part is never merged into a static batch (merged parts can't move). The village demo's forest (308 trees, 140 bushes) costs about 2.5 ms a frame in a Release build.

Volumetric fog

Scene Settings > Volumetric Fog fills the air with fog that is lit by the scene: the sun shines through it, and wherever the sun is blocked (behind a house, a tree) the fog stays dark, so you see light shafts. The sky lights it from all around, and point lights glow in it. It is saved with the level (the volumetricFog section of the scene's settings).

SettingWhat it does
Density, Base height, Height falloffHow thick the fog is at and below the base height, and how quickly it thins above it (to about a third every falloff metres): low ground mist, or a whole valley.
Wisps, Wisp scale, Wind speed / directionPatches of thicker and thinner fog that drift with the wind.
ColorTints the light the fog scatters.
Sun shafts, Forward scatteringHow bright the sunlit fog is, and how much brighter it gets looking towards the sun.
Sky light, Lamp glowLight from the sky, and the halo around point lights.
Distance, StepsHow far along each view ray it is computed, and how many samples are taken. It is computed at half resolution and sharpened against edges when it is put on the image.
For visible shafts, put the sun low and roughly in front of the camera, as the village demo does. The fog lies over glass as it does over the surface behind it.

Modular kits (Village)

Models come in any units, so the editor normally scales a model it places to 2 m across and stands it on the origin. A kit is a folder of pieces that must snap together, so they keep their own size and pivot instead: a model whose folder holds a kit.json file is loaded with Model::NativeSize. Placing one from the Assets panel (dragged onto the viewport or double-clicked) also snaps it to the 0.5 m grid, marks it Static (merged into static batches) and gives it a static Mesh body, so the nav grid sees it.

Examples/Assets/Models/Village is an abandoned-village kit made in Blender by Tools/village_kit.py (procedural textures, deterministic). Scenes/village.json is a demo village built from it.

Each piece is a .gltf with its .bin, and every piece uses the same texture atlas, village_atlas.jpg (the ground has its own repeating village_ground.jpg). A building piece therefore has one material and costs one draw per view; only iron fittings, rope and the well's water are separate small materials. The atlas holds 4 × 4 m of each texture (plaster, stone, wood, dark timber, shingles, bark), so a single face can be up to 4 m across. The engine loads each image once, whichever models use it: model textures are shared by file path, and embedded ones by content.

PiecesPivot and fit
wall, wall_window, wall_door, wall_broken, wall_ruin (about 1 m: half cover)2 m wide, 3 m high, 0.2 m thick, centred on its wall line, outside towards +Z. Bottom centre.

Keep walls, posts and roofs on whole metres (the editor's Snap moves by 0.5 m). Nav cells are 1 m, so a doorway centred on a whole metre has two cell centres in it, and the cells beside a wall stay walkable. Scripts/village_nav_test.lua checks this on the demo village (MDB_SCENE=village.json MDB_AUTOPLAY=1 MDB_TEST_SCRIPT=Scripts/village_nav_test.lua, 16 checks).

To change the kit, edit Tools/village_kit.py and run it with Blender (4.2 or later): blender --background --factory-startup --python Tools/village_kit.py -- <repo> [--preview <folder>] [--log <file>]. It rewrites the pieces, kit.json and village.json; --preview also renders every piece and a contact sheet.

Prefabs

A prefab is an entity with its children, saved as Assets/Prefabs/<name>.json. Each entity of an instance links to its prefab node. Instances keep overrides: changed fields, added or removed components, moved child transforms, and deleted child nodes.

  • Apply writes the whole instance back to the prefab; other instances keep their overrides on top.
  • Revert (per entity or per override) and Unpack (make it a plain entity).
  • When a prefab file changes, instances gain new parts and unlink removed ones on load.
  • Prefabs do not nest.
local coin = scene.spawn_prefab("coin", vec3(0, 1, 0))   -- Prefabs/coin.json

Rendering pipeline

SceneRenderer::Render draws one frame:

  1. Draw list: everything the camera or a light can see, culled and batched for instancing.
  2. Shadows: up to 4 point lights (cube maps) and one sun with cascades.
  3. Scene into an HDR framebuffer (colour, entity-ID for click picking, depth). PBR shading, then the sky, then decals (projected from a copy of the depth), then see-through surfaces back to front.
  4. SSAO, then bloom.
  5. Post: AO, bloom, exposure, tone mapping (ACES by default), gamma.
  6. FXAA. The result is a texture shown by the app.

Every scene draw is instanced: per-object data lives in a storage buffer; objects that share geometry, textures and alpha state are drawn with one call.

Materials & PBR

The lit shader is metallic-roughness PBR (Cook-Torrance GGX) with albedo, normal, metal/rough and emissive maps. Lighting is done in linear space; colour pickers and albedo/emissive textures are sRGB.

  • Metallic 0..1, Roughness 0..1, Emissive colour (above 1 glows with bloom).
  • Unlit: drawn as a bright emitter (intended for light markers).
  • Models can use their own materials (Use model materials).
self:add_mesh{ geometry = "sphere", color = vec3(0.9, 0.2, 0.2), metallic = 1, roughness = 0.25 }

Transparency

Alpha modeBehaviour
OpaqueNormal solid surface
CutoutPixels below the cutoff are discarded (fences, leaves)
BlendSee-through, premultiplied: diffuse fades with alpha, reflections stay (glass)

Alpha = texture alpha × material alpha × opacity. Blend surfaces are sorted per entity, back to front, and write no depth. Setting opacity below 1 on an opaque mesh switches it to Blend.

self.mesh.opacity = 0.4          -- now see-through
self:add_mesh{ geometry = "cube", texture = "texture:Textures/fence.png", alpha_mode = "cutout" }

Lighting & shadows

  • Sun (Directional Light): the first one is used. Cascaded shadows (1–4 cascades, stable while the camera turns). Viewport > Debug > Shadow Cascades tints them.
  • Point lights: up to 4, each with cube-map shadows.
  • Casters are culled per shadow view; the stats overlay shows how many were skipped.
  • Settings: shadow distance, cascade split, biases, extent (Scene Settings > Shadows).
local lamp = scene.spawn("Lamp", vec3(0, 3, 0))
lamp:add_light{ color = vec3(1, 0.7, 0.4), intensity = 2, shadows = true }

Environment & sky

Ambient light comes from image-based lighting: irradiance and prefiltered cube maps baked from an HDR panorama in Assets/Environments, or a procedural sky when none is loaded. Sky visibility, blur, rotation and ambient intensity are scene settings. Double-clicking an .hdr in the Assets panel makes it the sky.

Post-processing

  • SSAO: radius, bias, samples, strength (a post-multiply; Viewport > Debug shows it alone).
  • Bloom: threshold with soft knee, radius, intensity, brightness ceiling (no fireflies).
  • Tone mapping: ACES (default) and others, exposure, gamma.
  • FXAA anti-aliasing.

All are saved with the scene and edited in Scene Settings > Post Processing.

Batching, instancing & static merging

Objects with the same geometry part, textures and alpha state are drawn as one instanced batch. Skinned meshes are batches of one.

Static merging: Mesh Renderers marked Static that use a unique mesh are merged, when Play starts, into world-space chunks per material and 8 m cell. Repeated meshes stay instanced (that is faster). Moving or recolouring a merged entity during Play is not seen.

local s = scene.render_stats()
ui.text(s.draw_calls .. " draws, " .. s.static_merged .. " merged", 0.02, 0.95)

Skeletal animation

Models with bones (glTF/FBX) keep their skeleton and clips; the GPU skins up to 128 bones, 4 weights per vertex.

  • Clips with cross-fade when the clip changes.
  • Layers: another clip on a bone and its descendants (mask), override or additive, with fading weights.
  • Events at clip times → on_anim_event, or "sound:Sounds/x.wav" plays a sound.
  • Root motion: the root bone's travel moves the entity.
  • IK: look (head turns towards a target) and limb (two-bone reach), also in Edit mode.
self.animator:play("Run", 0.3)
self.animator:set_layer(1, { clip = "Survey", mask = "b_Neck_04", weight = 0, additive = true })
self.animator:layer_weight(1, 1, 0.6)                       -- fade in over 0.6 s
self.animator:set_ik(1, { type = "look", bone = "b_Head_05", target = player, max_angle = 75, chain = 2 })

Particles

CPU-simulated billboard particles. An emitter has a rate, burst, spread cone, shape (point, box…), gravity scale, drag, size and colour over life, emission brightness and optional texture/additive blending. Presets: Fire, Smoke, Sparks, Magic, Dust, Embers. Emitters preview live in Edit mode.

self:add_particles("Fire")
scene.spawn_particles(self.position, { preset = "Sparks", count = 40 })   -- one-shot, removes itself

Decals

Shapes projected down onto whatever is under them — floor, steps, ramps — for target circles, area templates, movement ranges and path markers. Scripts add them every frame (immediate mode, like the UI) into Scene::Decals.

  • Drawn after the opaque scene and the sky, before glass. The renderer copies the depth buffer, draws each decal as a box, rebuilds each pixel's world position and keeps the ones inside.
  • Fade on steep surfaces (walls, step risers) and towards the top and bottom of the box, so rings don't smear up walls.
  • Shapes: circle, ring (an outlined circle), square (grid cells), texture. Outline thickness, inside fill, softness, emission (above 1 glows).
  • Not clickable and not saved; one instanced draw per texture. scene.render_stats().decals counts them.
decal.draw(target, { size = 3, shape = "ring", color = vec3(1, 0.3, 0.2), thickness = 0.08, fill = 0.25 })

Physics

Jolt Physics, during Play only, at a fixed 60 Hz with interpolated transforms.

  • Body types: Static, Dynamic, Kinematic. Any body can be a trigger (sensor).
  • Shapes: Box, Sphere, Capsule (size.x diameter, size.y height), Convex hull, Mesh (static/kinematic), None.
  • Compound colliders: Collider components on children add shapes to the nearest body above them.
  • Events: exactly one begin and one end per touching pair; removed bodies end their contacts.
  • add_force lasts the frame; add_impulse applies once. Moving a static body from a script teleports it.
  • Raycasts (closest, all hits, static only). T in the editor throws a ball.
self:add_body{ type = "dynamic", shape = "sphere", size = 0.5, mass = 2, bounciness = 0.6 }
function on_collision_begin(self, other, hit)
    log("hit " .. other.name .. " at " .. tostring(hit.point))
end

Audio

miniaudio. One-shots (2D or positioned), and one voice per Audio Source that follows its entity (loop, volume, pitch, min/max distance). The listener follows the camera being drawn. Decoded clips are cached; Pause pauses the device, Stop stops all.

audio.play("Sounds/coin.wav")
audio.play_at("Sounds/thud.wav", self.position, { volume = 0.8, pitch = 1.2 })
self:add_audio("Sounds/lava_loop.wav", { loop = true, min_distance = 2, max_distance = 14 })

Navigation (NavGrid)

A layered walkability grid baked from static physics bodies. One grid serves both free movement (exploring) and grid movement (turn-based combat).

  • Bake: a ray down every column keeps each upward surface with head room and no wall within the agent radius. A column can hold several cells (ground under a bridge, and the deck).
  • Links to 8 neighbours when the height difference is a step and nothing blocks the way (a thin fence cuts the link). No corner cutting.
  • Free paths: A*, then straightened (any angle), ending exactly at the target.
  • Grid paths: cell centres with step costs (orthogonal 1, diagonal configurable).
  • Blocked cells for units and doors; reachable sets for movement ranges.

Baked lazily on first use (3.8 ms Release for the tactics level). Viewport > View > Navigation Grid draws it during Play. See Scripting › Navigation.

Line of sight & cover

Queries against the static level (the same bodies the nav grid is baked from):

  • Line of sight: a ray from the looker's eyes (1.5 m) to the target's chest (1.0 m). Units don't block it (they have no bodies).
  • Cover at a position against an attacker: three rays across the body (agent radius apart) about a cell towards the attacker. Blocked at waist height (0.6 m) is half cover (crates, fences); blocked at head height (1.5 m) too is full (walls, terraces).
  • Visible cells: every nav cell within a range that a point can see.

Measured on the tactics yard: half behind the crate and the fence, full against the terrace wall, none with the crate behind you. See Scripting › Line of sight.

Fog of war

Three states per nav-grid column: never seen (black), explored (dimmed — you remember the place, not what is there now) and visible (clear).

  • Each frame scripts reveal around their viewers. A column is visible if the viewer has line of sight to chest height there (walls and terraces cast vision shadows; low crates don't). Walls next to a seen floor are shown too.
  • Results are cached per viewer position, so a standing unit costs nothing; a new position costs about 2.5 ms in Debug.
  • Drawn as one fullscreen pass over the scene (from the depth buffer), with soft edges and fades. The sky is left alone and clicks still pick through it.
  • Hide units in the fog with e.visible = false (no shadow either).
  • The explored map is saved by the game (fog.save / fog.load in on_save / on_load).
  • Editor: Viewport › View › Fog of War turns the drawing off while play-testing.

See Scripting › Fog of war.

Game session & play mode

GameSession runs a scene as a game: Start (bodies, then scripts), Update, Stop. Both apps use it.

  • NewGame(level) starts a fresh campaign on the live scene.
  • Loads, level changes and restarts are requested during a frame and done by ApplyPending at the start of the next one.
  • Restart (scene.restart(), the pause menu) enters the current level again as it was entered.
  • The game camera is the primary Camera component (looks along local −Z).

Save games & levels

A level is saved as its differences from its scene file: changed and added entities in full, removed ones by ID. Saves are small (a few KB).

  • Transient entities (markers, particle bursts) are never saved.
  • Scripts save their variables with on_save / on_load.
  • game (campaign data) is kept across levels and saved; shared is per level.
  • Level changes keep the level you leave exactly as left; returning restores it. Entities can be carried along.
  • A save slot holds the current level, every visited level, game and play time; written safely (temp file, then rename).
  • Save folders: the game uses %APPDATA%\<title>\Saves (or --save-dir); the editor uses %APPDATA%\MDB Engine\Editor Saves (or MDB_SAVE_DIR).

Not saved: physics velocities, live particles, the nav grid, Lua locals without on_save. See Scripting › Save games.

Events, data files & Lua libraries

  • Event bus: events.emit(name, data) reaches every script's on_event after the frame's on_update (events emitted inside handlers are delivered in the same pass, up to 8 rounds).
  • Data files: data.load(path) reads any JSON under Assets as a Lua table.
  • Libraries: every Assets/Scripts/Lib/*.lua runs once in the shared globals when scripts start (the dialogue runner lives there).

Script UI rendering

Scripts produce a list of UI items each frame; the app draws them over the view with ImGui's draw list. Two layers build that list:

  • Positioned UI (ui.text/rect/bar/image/button with 0..1 coordinates).
  • Laid-out UI (UILayout): panels, rows, columns and scroll regions place widgets automatically. Sizes are in units (pixels at 720p), so the UI scales with resolution.

Item kinds: text (bold or regular font, optional shadow), rect, border, image (optionally 9-slice), button, clip push/pop. Fonts are Segoe UI Bold and Regular at 64 px.

Dialogue format

Dialogues are JSON files in Assets/Dialogues, edited visually in the editor's Dialogue Editor and played by Scripts/Lib/dialogue.lua.

Node typeFieldsBehaviour
linespeaker, text, action, event, choices, nextShows text; the player picks a choice or continues to next
branchcond, next, elseGoes to next if the condition is true, else to else
actionaction, event, nextRuns Lua and/or sends an event, then continues

Choices: text, cond, show (hidden or disabled), why (tooltip when disabled), action, event, next. next = 0 ends the conversation.

{ "version": 1, "start": 1, "nodes": [
  { "id": 1, "type": "line", "speaker": "Sage", "text": "You have {=game.gold or 0} gold.", "next": 0,
    "choices": [ { "text": "Buy a potion", "cond": "(game.gold or 0) >= 25", "show": "disabled",
                   "why": "You need 25 gold.", "action": "game.gold = game.gold - 25\ngive(\"potion\")", "next": 2 } ] },
  { "id": 2, "type": "action", "event": "potion_bought", "next": 0 } ] }

Projects

A game is a project: a folder of its own (its own git repo too) with project.json and Assets/. The engine repo stays separate; its shaders and Lua libraries (EngineAssets/) are shared by every project.

MyCRPG/
  project.json        the game's settings
  .gitignore          ignores Build/
  Assets/  Scenes/ Scripts/ Models/ Textures/ Sounds/ Prefabs/ Dialogues/ Environments/
  Build/              File > Build Game puts the shippable game here
// project.json (every field optional)
{ "title": "My Game", "scene": "main.json", "width": 1600, "height": 900, "fullscreen": true, "vsync": true,
  "exclude": ["Scripts/*_test.lua"] }
  • File › New Project: pick an empty folder; the project is made there and opened.
  • File › Open Project / Recent Projects: the editor restarts on that project (asking about unsaved changes first). It reopens the last project next time; the window title shows which one is open.
  • The editor opens the project's start scene. A new project starts with a simple scene named after it: Ctrl+S saves it.
  • Lua libraries: EngineAssets/Scripts/Lib loads first, then your project's Assets/Scripts/Lib.
  • Play-testing save slots are kept per project (%APPDATA%/MDB Engine/Editor Saves/<title>).
  • Examples/ in the engine repo is a project with every example level and test (File › Example Levels appears only there).

Build Game (shipping)

File › Build Game… makes a folder you can zip and ship. Set the title, start scene, window size, full screen, VSync and files to leave out (saved to project.json), pick the output folder, press Build.

  1. Compiles Game.exe in Release (the first time takes a few minutes; the editor keeps working, the log shows progress).
  2. Fills <output>/<title>/ with <title>.exe, EngineAssets/, your Assets/ (minus exclude) and project.json.

Play it runs the result and Show in Explorer opens the folder. The game uses the saved scene files, so save first. Players need the Microsoft Visual C++ Redistributable (x64), which most PCs have. A rebuild replaces the earlier build (only a folder that holds a project.json is ever replaced).

The standalone Game

Game.exe plays a project full screen or windowed, with no editor. It uses --project, else a project.json next to the exe (a built game), else the source tree's Examples. Its settings come from project.json.

Known limitations

  • Only the first sun and 4 point lights are used.
  • Transparency is sorted per entity, not per triangle; glass boxes show front faces only.
  • SSAO darkens direct light too; its blur is not depth-aware.
  • Animation: no blend trees or full-body IK.
  • Compound bodies don't rebuild when parts move during Play; Inspector body changes apply on the next Play.
  • Navigation bakes once, single-threaded, from static bodies only.
  • Saves: no thumbnails or file versioning.
  • UI: no keyboard/gamepad focus, no text input, Latin glyphs only.
  • Dialogue: no voice, portraits or localization; Lua errors appear at run time.

Undo & redo

Every scene edit is undoable without per-feature code: after each interaction the editor compares the scene with the last state and stores a new whole-scene snapshot if anything changed (up to 100). A whole drag or a typed name is one step, labelled like "Move Player" or "Delete Lava".

Ctrl+Z undo, Ctrl+Y or Ctrl+Shift+Z redo (Edit mode only). Scene settings and the editor camera are not tracked. Quitting or loading with unsaved changes asks first.

Play mode

  • Ctrl+P or the toolbar starts Play: the scene is snapshotted and physics, scripts, animation and audio run.
  • Pause and Step One Frame; Stop restores the snapshot (changes are discarded).
  • Play Through Game Camera: the viewport shows the primary Camera entity. Gizmos, picking and editor shortcuts are off then (except Esc, Ctrl+P, F1, F5), so games can use those keys.
  • F5 reloads shaders, and scripts too while playing.
  • Esc stops Play; in Edit mode it quits (asking about unsaved changes).
  • Level changes during Play bring their own render settings; Stop puts yours back.

Prefabs in the editor

  1. Select an entity (with children if you like) and click Save as prefab… in the Inspector.
  2. Place instances with Create > Prefab, the Hierarchy +, or by dragging the prefab from Assets.
  3. Edit an instance; its overrides are listed in the Inspector. Apply to prefab updates the prefab and every other instance (they keep their own overrides).

Scripting

Lua 5.4. Every entity with a Script component runs its file during Play, in its own environment.

Getting started

  1. Assets panel > right-click > New Script (or create Assets/Scripts/spin_up.lua).
  2. Drag it onto an entity (or Inspector > Add Component > Script).
  3. Press Play. Edit and press F5 to reload while playing.
-- spin_up.lua: rises and turns
local speed = 1.5

function on_create(self)
    log("hello from " .. self.name)
end

function on_update(self, dt)
    local p = self.position
    self.position = vec3(p.x, p.y + 0.2 * dt, p.z)
    self.rotation = self.rotation + vec3(0, speed * dt, 0)
end

Each entity gets its own copy of the script's globals. A script that errors is switched off and the error appears in the Console.

World to screen

Dialogue

Dialogues are made in the Dialogue Editor. Play one from any script:

local talk
function on_update(self, dt)
    if not talk and input.key_pressed(Key.T) then
        talk = dialogue.open("sage", { speaker = self })      -- Dialogues/sage.json
    end
    if talk and not talk:update() then talk = nil end        -- draws the default box until it ends
end

Or give an entity npc.lua: it plays Dialogues/<its name in lower case>.json when the hero is close and presses T.

Inside a dialogue

  • Conditions are Lua expressions: game.gold >= 25, has_item("gem"), not game.met_sage.
  • Actions are Lua statements: game.gold = game.gold - 25; give("potion").
  • They see the globals, speaker (the entity talking) and every function in dialogue.helpers.
  • Text takes UI markup and {=expr}: You have {=game.gold or 0} gold.
  • Events go to every script's on_event with { dialogue, node, speaker }; the runner also sends dialogue_started and dialogue_ended.
-- add your own helpers for dialogue code
dialogue.helpers.reputation = function(faction) return (game.rep or {})[faction] or 0 end

-- react to a dialogue event
function on_event(self, name, data)
    if name == "magic" and data.speaker == self then scene.spawn_particles(self.position, "Magic") end
end

-- draw it yourself instead of talk:update()
ui.label(talk.speaker .. ": " .. talk.text)
for i, o in ipairs(talk.options) do
    if ui.button(o.text, { disabled = not o.enabled, tooltip = o.why }) then talk:choose(i) end
end
if #talk.options == 0 and ui.button("Continue") then talk:continue() end
