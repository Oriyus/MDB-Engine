Engine

The runtime: rendering, scenes, physics, audio, animation, navigation, save games and the systems both apps share.

Overview & architecture

MDB Engine is a C++20 game engine for Windows using OpenGL 4.5 (core profile, direct state access). The engine is a static library, Engine, used by two apps:

  • MDBEditor — the editor (folder Editor/).
  • Game — the standalone player with no editor (folder Game/).

Application runs the main loop and calls the virtual hooks OnStart, OnUpdate(dt), OnImGui and OnShutdown. Each app defines Engine::CreateApplication().

Shared runtime

  • SceneRenderer renders a scene through a camera into a texture (the editor shows it in the Viewport, the game draws it full window).
  • GameSession owns physics, audio, prefabs, scripts and navigation, steps them in order, and is also the campaign (save slots, level changes).
  • ResourceLibrary maps resource names ("cube", "model:Models/Fox.glb") to loaded meshes and textures.

One frame of play

  1. Pending loads, level changes and restarts are applied (GameSession::ApplyPending).
  2. Scene::OnUpdate: Spin, Orbit, animation, particles.
  3. Animation events, then Lua on_update, then queued events.emit events.
  4. Physics step (fixed 60 Hz, interpolated), then collision and trigger callbacks.
  5. Audio follows its entities; the scene is rendered.

Entities & components

Scenes use an ECS (EnTT). An Entity is a thin handle with Add<T>, Get<T>, Has<T> and Remove<T>. Every entity has a name (Tag), a Transform and a stable 64-bit ID.

Rigid BodyPhysics body: type, shape, size, centre, mass, friction, bounciness, trigger, lock rotation (dynamic: physics moves it but never turns it, for characters)

Adding a new component type means updating Components.h, the snapshot code in Scene, the JSON functions in Scene/EntityJson.cpp, and the editor's Inspector.

Transforms & hierarchy

A child stores its parent's ID (ParentComponent) and its transform is local to the parent. Everything spatial (rendering, physics, audio, cameras, the gizmo) works in world space.

  • GetWorldMatrix, SetWorldMatrix / Position / Rotation, SetParent(child, parent, keepWorld) (refuses loops), GetChildren.
  • Destroying an entity destroys its children; duplicating copies the whole subtree with new IDs.
  • Static and kinematic bodies follow their parent; dynamic bodies simulate in world space.
Rotations are stored as Euler angles. Convert a quaternion back with Scene::EulerFromQuat, never glm::eulerAngles (it is unstable near gimbal lock and made cameras shake).

Grass and flowers (Foliage)

A Foliage component (Create > Grass, or Add Component > Foliage) covers an area of the entity's X/Z plane with grass and flower clumps. The clumps are generated from the settings and the Seed, so scene files store only the settings. They are drawn GPU-instanced, about one draw per 8 m chunk in view, and lit by the same shader as everything else: sun shadows, lights, sky light and fog of war all fall on them.

SettingWhat it does
Size, Density, SeedThe area (metres, centred on the entity), clumps per m², and which random layout. New seed picks another.
Avoid static objectsNo grass on the footprint of Static meshes: the outline (convex hull) of their vertices from 0.5 m below to 0.35 m above the ground under them (a terrain's surface, or the field's height), grown by 5 cm. So walls, posts, trunks and props keep their own shape (a rotated wall clears a thin strip, a round tower a circle), and grass still grows under fence rails and branches. Per object (Mesh Renderer, when Static): Blocks grass off lets grass grow through it; margin grows the footprint (negative shrinks it). Objects lying flat on the ground (floors, ground tiles) and ones starting 1 m or more above it are left out. Moving them scatters the grass again.
Follow terrainOver a terrain, clumps stand on its surface instead of the entity's height (on by default; without a terrain nothing changes).
Grows onAnywhere, or only where one terrain layer is painted: paint grass layer → grass grows, paint rock over it → it goes. The share of paint decides, so edges thin out.
Height, Height variation, WidthClump size; flowers stand a little taller.
Root / Tip / Dry color, Dry patches, FlowersBlades shade from root to tip; dry patches turn the tips to the dry colour; Flowers is the share of flower clumps.
Wind strength, speed, directionGusts roll across the field along the direction (0° blows towards +X, 90° towards +Z), and every clump flutters a little.
Interaction, RecoveryHow far things bend the grass when they move through it, and how many seconds it takes to stand up again (leaving trails).
Draw distanceThe grass thins out smoothly over the second half of it.
Ground shadeHow much the grass darkens the ground under it (0..1, default 0.6): less sunlight, and half as much less sky light, where the clumps grow. A steady stand-in for the shade of the blades, which cast no shadows of their own; it fades out with the grass.

What presses the grass: every dynamic or kinematic rigid body (not triggers) near it, sized by its collider, and foliage.push from scripts. Clicks go through the grass to whatever is under it. The village demo has 11,600 clumps (about 790,000 triangles), which cost about 0.7 ms a frame in a Debug build.

Grass receives shadows but casts none. Off a terrain it stands on the entity's flat plane. While a terrain is being sculpted or painted, the grass on it scatters again at most every quarter second.

Grass Blockers

A Grass Blocker (Create > Grass Blocker, or Add Component) keeps every grass field out of an area you shape by hand: a path, a yard, the ground under a table. It lies in its entity's X/Z plane, so moving, rotating and scaling the entity moves, aims and stretches it.

SettingWhat it does
ShapeBox (size X by Z), Circle (diameter) or Capsule (length end to end along the entity's X, and width): rotate a capsule to lay a path.
Soft edgeThe grass thins out over this many metres inside the edge instead of stopping at a line (which spots stay is fixed, so it doesn't change between scatters).

In the editor it shows as a green outline on the ground (following a terrain), a fainter inner outline where a soft edge reaches full strength, and a diamond at its centre; click the outline or the diamond to select it (clicks inside it still pick what is on the ground). Viewport > View > Grass Blockers hides them. It is never rendered, and it works whether or not a field avoids static objects.

Terrain

A Terrain component (Create > Terrain, or Add Component > Terrain) is a heightmap: a square grid of heights spread over Size metres of the entity's X/Z, centred on it, painted with up to four layers. The entity's transform places it (moving, rotating and scaling all work; a Y scale stretches the heights).

PartHow it works
HeightsResolution 33 to 1025 samples per side (129 for a new terrain, 257 in the demo). Each grid square is two triangles split from corner (x, z) to (x+1, z+1), the same split as the physics height field, so what you see, what bodies stand on and what terrain.height says agree (within 2 mm in the test).
DrawingChunks of 32 × 32 squares, each its own mesh, culled on its own, through the usual draw list: shadows (cast and received), the depth pre-pass, TAA, click picking, the selection outline and every Viewport shading mode work as for any mesh. A sculpted chunk is rebuilt the same frame.
LayersEach layer has a colour tint, an optional texture repeating every Tiling metres, and a roughness. A paint map (RGBA, two texels per grid square, at most 1024²) holds each layer's share. Height blend treats a texture's brightness as its height where layers meet, so stones and thick grass show through first instead of a soft fade (0 = plain mixing). Variation (per layer, default 1) breaks up the repeat with stochastic hex tiling: the texture is laid as randomly shifted and turned copies, blended along its own dark lines, so no pattern shows across big areas. It costs three texture reads instead of one, and only where the layer is painted. Turn it down for textures with a direction, such as rows or light from one side (0 = a plain repeat).
Layer mapsUnder each layer, Maps takes three optional images from Assets that repeat with the colour texture: a normal map (tangent space, OpenGL style with green pointing up the image; tick DirectX for maps whose green points down, often named _nor_dx), with a normal strength; a grey roughness map (multiplied by the layer's roughness slider, which is set to 1 when you add one); and a grey height map, which height blending and the stochastic seams use instead of the colour's brightness. Find maps next to the texture fills them from images beside the colour texture with the usual endings (_normal, _nor_gl, _nrm, _roughness, _rough, _height, _disp...). The engine packs the three into one texture per layer (re-read when a file changes; a smaller map is stretched to the largest one's size), and stochastic tiling turns each copy's normals with it. A layer that isn't painted at a pixel costs nothing there. The example terrain's maps are made by Tools/terrain_textures.py.
CollisionA Rigid Body with shape Terrain (Create > Terrain adds a static one; the Inspector has Make solid) is a Jolt height field. The navigation bake sees it like any static body. It can't be dynamic.
FilesHeights and paint are not in the scene file: they are in Assets/Terrains/<name>.terrain (named after the scene; the scene stores the path and a hash of the contents). The editor writes them every time it saves the scene. A duplicated terrain gets a file of its own when it is saved with different contents. Build Game copies them with the rest of Assets.
GrassFoliage fields follow the terrain's surface and can grow only on one painted layer (see Grass).

Measured on the terrain demo (120 × 120 m, 257², 64 chunks, 19,000 grass clumps on the grass layer): 144 FPS in the Debug editor at 1600 × 900 on an RTX 2060.

Level of detail. Far from the camera, a chunk is drawn with every 2nd, 4th, 8th or 16th sample instead of all of them, as long as the ground stays within Scene Settings > Levels of Detail > Terrain error pixels of the full surface (default 1, measured at 1080 lines; 0 draws everything at full detail; scene.terrain_lod_error in scripts). Flat ground goes coarse close up, rough ground stays detailed further out. Neighbouring chunks differ by at most one level and their edges are stitched, so there are no cracks. Physics, raycasts, terrain.height and grass always use the full heights. Viewport > Debug > LOD Levels colours chunks by level (green full, yellow, orange, red, purple). On a 1 km, 1025² terrain the triangles in view went from 1.24 million to 0.52 million and the GPU frame from 4.3 to 3.2 ms (2.7 ms at 2 pixels), with no visible difference.

Undo keeps whole copies of the heights or the paint per stroke (copy on write: a sculpt stroke copies only the heights), about 1 MB per step on a 257² terrain and 4 to 5 MB on 1025².

Wind (trees)

Any Mesh Renderer can sway in the wind: set its Wind (0 = still, 1 = a tree). The higher a point is in the mesh, the more it moves, so trunks stay planted while crowns bend with the gusts and the leaves flutter. Shadows sway with it. The wind itself is in Scene Settings > Wind (direction, speed, strength) and is saved with the level. It blows in Edit mode too, so you see it while building.

The gusts roll across the level the same way as on the grass, so trees and the grass under them move together. Grass fields keep their own wind settings (Foliage component). Scripts: self.mesh.wind = 0.8 or add_mesh{ ..., wind = 1 }.

A swaying part is never merged into a static batch (merged parts can't move). The village demo's forest (308 trees, 140 bushes) costs about 2.5 ms a frame in a Release build.

Color grading

Scene Settings > Post Processing > Color grading shapes the final picture. It is saved with the level; the default values change nothing, and Reset grading goes back to them.

SettingWhat it does
ContrastAbove 1, shadows get deeper and lights brighter (around mid grey).
Saturation0 is black and white, above 1 is richer colour.
Temperature, TintWhite balance: cooler (blue) or warmer (orange), and green against magenta.
Shadow tint, Highlight tintA colour for the dark parts and one for the bright parts. Cool shadows with warm highlights is the classic film look.
VignetteDarkens the corners, drawing the eye to the middle.
Film grainFine moving noise; about 0.02 is visible without being distracting.
If the picture looks washed out, look at the volumetric fog first. Fog adds light over everything, so a near-white fog colour, strong sun shafts or sky light turn every shadow grey. Lower those (and the density), then use Exposure and Contrast. With a low sun behind the scene, check a view that looks away from the sun too: it is mostly shade, and too much contrast makes it black.

Volumetric fog

Off by default; each scene keeps its own setting (a scene without one has no fog). Scene Settings > Volumetric Fog fills the air with fog that is lit by the scene: the sun shines through it, and wherever the sun is blocked (behind a house, a tree) the fog stays dark, so you see light shafts. The sky lights it from all around, and point lights glow in it. It is saved with the level (the volumetricFog section of the scene's settings).

SettingWhat it does
Density, Base height, Height falloffHow thick the fog is at and below the base height, and how quickly it thins above it (to about a third every falloff metres): low ground mist, or a whole valley.
Wisps, Wisp scale, Wind speed / directionPatches of thicker and thinner fog that drift with the wind.
ColorTints the light the fog scatters.
Sun shafts, Forward scatteringHow bright the sunlit fog is, and how much brighter it gets looking towards the sun.
Sky light, Lamp glowLight from the sky, and the halo around point lights.
Lamp shaftsShadowed point lights cut shafts in the fog too (spot lights always do). Off by default: a shadow lookup per lamp per step, about 0.7 ms with the village's 4 lamps.
Distance, StepsHow far along each view ray it is computed, and how many samples are taken. It is computed at half resolution and sharpened against edges when it is put on the image.
For visible shafts, put the sun low and roughly in front of the camera, as the village demo does. The fog lies over glass as it does over the surface behind it.

Modular kits (Village)

Models come in any units, so the editor normally scales a model it places to 2 m across and stands it on the origin. A kit is a folder of pieces that must snap together, so they keep their own size and pivot instead: a model whose folder holds a kit.json file is loaded with Model::NativeSize. Placing one from the Assets panel (dragged onto the viewport or double-clicked) also snaps it to the 0.5 m grid, marks it Static (merged into static batches) and gives it a static Mesh body, so the nav grid sees it.

Examples/Assets/Models/Village is an abandoned-village kit made in Blender by Tools/village_kit.py (procedural textures, deterministic). Scenes/village.json is a demo village built from it.

Playing the village. Press Play: a blue box, the "Player", walks with W A S D (relative to the camera), runs with Shift and jumps with Space and crouches while C or Ctrl is held. The game camera follows it (follow.lua) and comes in when a wall, house or trunk gets between them, so it never ends up inside one (leaves have no collider, so it can still look through a canopy). The player is a Character Controller: walls, fences, trees and houses with colliders stop it, it slides along them, walks up steps and kerbs, and pushes loose objects. Scripts/village_player.lua has the speeds, acceleration, jump height and crouch height at the top. Running village_kit.py again regenerates village.json and loses the player, along with any other changes made in the editor.

Each piece is a .gltf with its .bin, and every piece uses the same texture atlas, village_atlas.jpg (the ground has its own repeating village_ground.jpg). A building piece therefore has one material and costs one draw per view; only iron fittings, rope and the well's water are separate small materials. The atlas holds 4 × 4 m of each texture (plaster, stone, wood, dark timber, shingles, bark), so a single face can be up to 4 m across. The engine loads each image once, whichever models use it: model textures are shared by file path, and embedded ones by content.

Prefabs

A prefab is an entity with its children, saved as Assets/Prefabs/<name>.json. Each entity of an instance links to its prefab node. Instances keep overrides: changed fields, added or removed components, moved child transforms, and deleted child nodes.

  • Apply writes the whole instance back to the prefab; other instances keep their overrides on top.
  • Revert (per entity or per override) and Unpack (make it a plain entity).
  • When a prefab file changes, instances gain new parts and unlink removed ones on load.
  • Prefabs do not nest.
local coin = scene.spawn_prefab("coin", vec3(0, 1, 0))   -- Prefabs/coin.json

Rendering pipeline

SceneRenderer::Render draws one frame:

  1. Draw list: everything the camera or a light can see, culled and batched for instancing.
  2. Depth pre-pass: the solid scene and the grass are drawn once without lighting, so the lighting below runs once per pixel instead of once per overlapping leaf or grass blade.
  3. Scene into an HDR framebuffer (colour, entity-ID for click picking, motion vectors, depth): the solid scene and the grass with PBR shading, then SSAO multiplied into them, then the sky, decals (projected from a copy of the depth), see-through surfaces back to front, volumetric fog and particles.
  4. Temporal anti-aliasing: the frame, drawn shifted by a sub-pixel amount, is blended with the frames before it.
  5. Bloom.
  6. Post: bloom, exposure, tone mapping (ACES by default), colour grading, gamma.
  7. FXAA (only when TAA is off). The result is a texture shown by the app.

Every scene draw is instanced: per-object data lives in a storage buffer; objects that share geometry, textures and alpha state are drawn with one call.

Materials & PBR

The lit shader is metallic-roughness PBR (Cook-Torrance GGX) with albedo, normal, metal/rough and emissive maps. Lighting is done in linear space; colour pickers and albedo/emissive textures are sRGB.

  • Every look lives in a material: colour and colour map, metallic, roughness, specular, emission, normal map, unlit (below). The Mesh Renderer only says which material each part uses, plus per-object transparency, shadows, wind and levels of detail.
  • A part with no material file uses the model file's own material (Use model materials), else the built-in Default (white, roughness 0.5).
  • Unlit materials draw their colour as a bright emitter, with no lighting or shadows.
self:add_mesh{ geometry = "sphere", material = "Materials/gold.mat" }

Material files (.mat)

A material file, Assets/Materials/<name>.mat, is a reusable surface: make it once, then use it on any Mesh Renderer part and any terrain layer. Change the file and everything using it changes with it, also while playing. It is JSON, and every key is optional:

{
  "version": 1, "shader": "standard",
  "color": [1, 1, 1], "albedoMap": "Textures/Terrain/rock.jpg",
  "alphaMode": "opaque", "alpha": 1, "alphaCutoff": 0.5, "doubleSided": false, "castShadows": true, "unlit": false,
  "metallic": 0, "roughness": 1, "specular": 1,
  "metalRoughMap": "",                        // packed like glTF: green = roughness, blue = metallic
  "roughnessMap": "Textures/Terrain/rock_rough.png", "metallicMap": "",   // grey maps, used without a packed one
  "normalMap": "Textures/Terrain/rock_normal.png", "normalStrength": 1, "normalFlipY": false,   // DirectX-style when flipped
  "emissive": [0, 0, 0], "emissiveIntensity": 1, "emissiveMap": "",
  "heightMap": "Textures/Terrain/rock_height.png",   // terrain layers blend by it
  "uvScale": [1, 1], "uvOffset": [0, 0]
}
  • Variants. A file with "parent": "Materials/stone.mat" starts as its parent and holds only the values it changes, so later edits to the parent reach it too (Materials/Terrain/rock_mossy.mat is a greener rock at twice the repeat).
  • On meshes. Inspector > Mesh Renderer > Materials has a slot per part (a model's submeshes, one for a shape). A part draws with its slot's material; the Mesh Renderer's Opacity multiplies its alpha. An empty slot shows "(the model's own)" or "(Default)". Make saves a part's current look as a new file. Dropping a material from Assets on an object in the Viewport or a Hierarchy row gives every part that material.
  • On terrain. Inspector > Terrain > Layers: a layer's material gives its colour map and tint, roughness, normal, grey roughness and height maps. Tiling and Variation stay the layer's. The terrain example (terrain.json) uses Materials/Terrain/{grass,earth,rock,sand}.mat. Metallic and the packed metal/rough map are not used on terrain.
  • Batching is unchanged. Values travel per instance, so parts with different materials but the same textures still draw together. A material's UV scale/offset and normal strength sit in spare room of the instance data. Static merging bakes the UV placement into the merged vertices.
  • A missing file draws magenta, and the part fills in once the file appears. Files changed outside the editor are read again within a second.
  • "shader" names the shader the values feed: only "standard" (lit.frag's PBR) so far. Node-based shader graphs are the next step.
  • Per-object overrides. A script can give one object its own colour, emissive, metallic or roughness on top of its material (self.mesh.color = ..., add_mesh{ color = ... }): hazards that pulse, a highlighted unit. The editor shows them under Materials with a Clear button but never makes them. They are saved only when set, so save games keep a script's tints.
  • Older scenes and prefabs kept the look on the Mesh Renderer itself. When one loads in the editor, each distinct look becomes a material file under Materials/Generated/, named after the first object that had it and shared by every object with the same values. Save the scene to keep it in the new form. A tint on a model's own materials becomes a colour override instead. The Game converts in memory and never writes files.
self:add_mesh{ geometry = "sphere", material = "Materials/gold.mat" }
self.mesh.material = "Materials/glow.mat"            -- every part
self.mesh.materials = { "Materials/a.mat", "" }      -- per part ("" = the model's own or the Default)
self.mesh.emissive = vec3(2, 0.3, 0)                 -- this object only (an override)
self.mesh:clear_overrides()                          -- back to the material's values
local m = material.get("Materials/gold.mat")         -- every value after the parent's
material.set("Materials/glow.mat", "emissiveIntensity", 6)   -- for everything using it, until Play stops

Shader graphs

A shader graph (Assets/Shaders/<name>.shadergraph) designs a surface as a network of nodes, like Unity's Shader Graph, Amplify Shader or Unreal's material editor. A material uses it with "shader": "Shaders/x.shadergraph". The graph describes the surface only: base colour, alpha, metallic, roughness, specular, normal (tangent space) and emission, plus a vertex offset; the inputs of its Output node. Lights, cascaded shadows, image-based light, fog of war, TAA and the editor's view modes stay the engine's, so a graph material is lit and shadowed like any other.

  • Params are the values a graph exposes: float, vec2, vec3, vec4, color (sRGB in pickers, linear in the shader) and texture (with a Data (linear) switch for normal maps, roughness and masks). Each material using the graph sets its own in "params", so one graph serves many materials. A variant's params are merged into its parent's one by one.
  • Nodes, about 60:
    • Input: UV, Position, Normal, View Direction, Screen Position, Time, Float, Vector2/3/4, Color, Property.
    • Texture: Sample Texture, Sample Normal Map, Triplanar.
    • UV: Tiling And Offset, Panner, Rotate UV, World UV.
    • Math: Add, Subtract, Multiply, Divide, Power, Min/Max, Modulo, Step, One Minus, Negate, Absolute, Floor, Ceiling, Fraction, Square Root, Sine, Cosine, Saturate, Normalize, Clamp, Lerp, Smoothstep, Remap, Posterize, Length, Distance, Dot and Cross Product.
    • Vector: Split, Combine.
    • Procedural: Noise, Fractal Noise, Voronoi, Checker, Gradient, Waves (four directional sine waves at deep-water speeds: Height for a Vertex Offset, a matching tangent-space Normal for the plane / grid's UVs, and Slope for foam).
    • Surface: Fresnel, Desaturate, Contrast, Hue Shift, Normal Blend, Normal Strength, Height Blend.
    • Logic: Compare.
    Math nodes take any size: a number goes into any vector, a wider vector into a narrower input keeps its first components.
  • Render state is the material's: alpha mode and cutoff, double-sided, cast shadows, unlit. A graph whose Alpha is connected cuts the depth pre-pass and the shadows too (a Cutout material: holes cast holes).
  • How it runs. The graph compiles to one GLSL function, put into lit.frag, depth_prepass.frag, shadow.frag and sun_shadow.frag at // @GRAPH_CODE. Each graph has those four programs, built on first use and shared by every material using the graph. Batches are sorted by graph; switching to one replays the lighting values the plain shader got that pass. Param values are uniforms per batch, and textures use units 22 to 31 (at most 10 per graph). The object's tint (a script's e.mesh.color, Opacity) multiplies the graph's colour, and its emissive (hit flash) adds to the graph's emission.
  • A graph with errors draws its materials magenta. F5 rebuilds every graph's programs.
  • Examples: Shaders/lava (panning fractal noise into emission), rim_glow (fresnel), dissolve (noise against an Amount cuts the surface, with a glowing edge), triplanar_rock (a rock texture from the world axes). Each has a material with the same name in Materials/, as has wobble (vertex offset, below).
self:add_mesh{ geometry = "sphere", material = "Materials/dissolve.mat" }
material.set_param("Materials/dissolve.mat", "Amount", 0.7)        -- every object using it, until Play stops
material.set_param("Materials/lava.mat", "Hot", vec3(0.2, 0.9, 0.3))
log(material.get("Materials/lava.mat").error)                        -- "" when it compiles

Vertex Offset (an Output input, world space, metres) moves the mesh's points: waves, wobble, breathing, custom wind. It is compiled into a second function for lit.vert and shadow.vert, so the depth pre-pass, both shadow passes and the motion vectors (evaluated at last frame's time) all move with it; such a graph always draws with its own programs. Its inputs there: UV, position and normal before the offset, Time (no view direction or screen position). Normals are not recomputed (feed a matching Normal if the lighting should follow), a mesh needs enough vertices to bend (the built-in plane has four), and culling still uses the undisplaced bounds, so keep offsets small or the object can vanish at the screen edge. Examples: Shaders/wobble (a travelling sine wave along the normal) and Shaders/water, each with its material.

Water (Shaders/water.shadergraph, Materials/water.mat: Blend, no shadows). Big waves (a Waves node fed by the Direction, Wavelength, Wave height and Speed params) move the vertices, and their normal is blended with small ripples. The colour goes from Deep in the troughs to Shallow on the crests. Fractal noise drifting over world UVs, plus the wave height, makes foam on the crests (Foam amount); foam is also rougher and opaque. Alpha rises with fresnel, so the water is clearer looking down and reflects the sky towards the horizon. Specular (how shiny a non-metal is)

Every non-metal surface reflects a little light: about 4% when you look straight at it, rising to a bright sheen at grazing angles. On dark, rough materials such as bark, soil or cloth, that sheen can read as an unwanted plastic or wet look. Lower it with the material's Specular slider (Material Editor; 1 = the usual reflection, 0 = none at all). Metals are not affected: their reflection is their colour.

Models can set it too. In Blender, the Principled BSDF's Specular IOR Level exports as glTF KHR_materials_specular, which the engine reads (0.5 in Blender is the normal amount and exports as 1; 0 exports as 0, no reflection). Lowering roughness does the opposite of what you might expect here: a fully rough surface (roughness 1) still has the grazing sheen, so use Specular to remove it.

log(self.mesh.specular)           -- read only: set it in the material file
material.set("Materials/bark.mat", "specular", 0)   -- matte, for everything using it (until Play stops)

Vertex colours: weathering on buildings, wind on plants

A glTF model's vertex colours (COLOR_0) mean different things depending on the asset's category, a custom property named category that exports as a glTF extras entry. The engine looks in the file's asset, then its scenes, nodes (Blender objects), meshes and materials. The first one found decides, and case does not matter.

  • Architecture (the category's first part is Architecture, e.g. Architecture/Castle_Stone): the colour multiplies the base colour and alpha. Use it for baked weathering: dirt on ledges, rain streaks, rising damp, occlusion in doorways.
  • Vegetation (a wind extra, or a category starting with Nature or Vegetation): the colour is wind data and never tints. R is the main bend (0 at the ground, 1 at the top). G is the branch bend (0 on the trunk). B gives each branch its own timing. A is the leaf flutter (0 on wood). The tree then sways by these weights instead of by height, in its shadow too. Placing such a model sets its Mesh Renderer Wind to 1. The scene's Wind settings and that slider still control how strongly it moves.
  • Anything else, and FBX / OBJ files: vertex colours are ignored.

The Console says which way a model's COLOR_0 was read when it loads.

{ "nodes": [ { "name": "SM_Castle_Wall", "extras": { "category": "Architecture/Castle_Stone" } }, ... ] }
{ "nodes": [ { "name": "SM_Tree_Broadleaf_01", "extras": { "category": "Nature/Trees", "wind": "COLOR_0 R=main bend ..." } }, ... ] }

Cut-out foliage at a distance

Smaller mipmap levels of a texture are averages of the bigger ones. For thin cut-out shapes (willow leaves, grass blades, chain links), that turns solid alpha into faint alpha below the cutoff, so leaves used to thin out and disappear as trees got further away. When a texture is first drawn as Cutout, the engine rebuilds its mipmaps so that each smaller level lets as many pixels through the cutoff as the full-size image does. Distant foliage then stays as dense as it looks up close. It happens automatically, once per texture, for model materials and Mesh Renderer textures alike. All textures also use anisotropic filtering (up to 16×), which keeps surfaces seen at a slant (ground, roofs, hanging leaf cards) sharp in the distance.

Double-sided

Normally only the front of a surface is drawn: from behind, a single plane (a leaf card, a sign, a flag, a paper sheet) is invisible. Tick Double-sided on the Mesh Renderer to draw the back faces too. Each side is lit as facing its own way, so the back is not dark, and the part casts a shadow whichever side faces the light. A model's materials can also ask for it: glTF doubleSided is read on import, and with Use model materials a part is double-sided when either the Mesh Renderer or its material says so (the Inspector tells you when the file does).

Use it only where it's needed: back faces cost drawing time on those objects. A closed object (a box, a barrel) never needs it. Note that Blender writes doubleSided: true for any material with Backface Culling off, which is its default; tick Backface Culling in the material settings before exporting a closed model. Tools/village_kit.py removes the flag from the village kit for this reason.

self.mesh.double_sided = true
self:add_mesh{ geometry = "plane", texture = "texture:Textures/fence.png", alpha_mode = "cutout", double_sided = true }

Lighting & shadows

  • Sun (Directional Light): the first one is used. Cascaded shadows (1–4 cascades, stable while the camera turns). Viewport > Debug > Shadow Cascades tints them.
  • Point lights: as many as you like (up to 4096 drawn). Each has a Range (Inspector, metres): it fades smoothly to nothing there. 0 means automatic, worked out from its brightness (a white light of intensity 1 reaches about 70 m, at most 100 m). Many lights are cheap when their ranges are short: the view is cut into 16 × 9 screen tiles × 24 depth slices (clusters), each listing the lights that reach into it, and a pixel weighs only the lights of its cluster. Measured (Release, RTX 2060, 1600 × 900, Scenes/lights.json): 1.8 ms a frame with no lamps, 2.6 ms with 256 lamps of 3 m range, 3.5 ms with 1024. Viewport > Debug > Light Clusters tints the picture by how many lights each pixel weighs (blue 1, green 2, yellow 4, orange 8, red 16 or more); the stats overlay shows lights seen / total and the most in one cluster.
  • Spot lights: a point light with a cone (Create > Spot Light, or tick Spot light on a point light). It shines along the entity's local −Z like the sun: aim it with Rotate (E). Cone angle is the full angle edge to edge; Soft edge is how much of the cone fades out towards its edge (0 a hard edge). Spot lights light the volumetric fog too (beams), go through the same clusters (only where the cone reaches), and with Casts shadows they get a shadow map in the shadow atlas (one view of the cone: cheaper than a point light's six; cones wider than 120° take cube faces instead). Their shadows also cut light shafts in the volumetric fog.
  • Cookies: any light can shine through an image (Inspector > Cookie, or drop a texture on it): a window frame, leaves, stained glass, a pierced lantern. A spot light projects it along its cone; a point light wraps it round itself as a 2:1 panorama whose middle faces the entity's local −Z. The top follows the entity's local +Y. The cookie colours the light, shadows and fog shafts included. An animated cookie is a grid of frames in one image (left to right, top row first): set Flipbook frames (columns × rows) and Frames a second (0 holds the chosen Frame). Up to 12 different cookie and profile images can be in view at once. Very wide spot cones stretch the image towards their edge.
  • Light profiles (IES): the .ies files lamp makers publish describe how bright a lamp is in every direction. Pick one in Inspector > Light profile (any .ies file under Assets) and the light takes its shape: a downlight's pool, a wall washer's fan. 0° of the profile points along the entity's local −Z, so aim a ceiling light down (Rotate X −90°). The profile shapes the light only; Intensity still sets how bright it is.
  • Scenes/lights.json shows each kind: the left spotlight shines through Textures/window.png, the right one through a turning fan (Textures/fan_cookie.png, 4 × 2 frames at 12 a second), the orange torch through a lantern (Textures/lantern_cookie.png), and the Ceiling Lamp uses Lights/downlight.ies.
  • Sorting lights into clusters runs on the GPU (a compute shader); it frees the CPU (0.58 ms a frame with 4096 lights) for about 0.1–0.2 ms of GPU time. Viewport > Debug > GPU Light Binning switches it off to compare (the stats overlay says which is in use).
  • In the Viewport a selected point light shows its range: the sphere's outline, a faint ring at its height and the distance beside the bulb ("auto" when automatic). Spot lights show their cone: a short one always, so you see where they point, and out to the range when selected, with the soft edge's inner cone fainter. Drag the white dots to change it: the dot on the range (a spot's tip) sets the Range, the dot on a spot's rim its Cone angle.
  • Light shadows: every shadowed light (point or spot) gets its shadows from the shadow atlas: one big shadow texture shared out in squares (a point light takes six, one per side of a cube; a spot one). The 4 most useful are shaded directly and get the biggest squares. Scene Settings > Shadows > Atlas lights (0–64, default 24) sets how many more at a time, Atlas size (1024–8192, default 8192, 128 MB) how big the texture is. Viewport > Debug > Shadow Atlas shows it in a corner, every light's squares outlined and named. Each light's squares are sized by how much of the view its light covers, so near lights get sharp shadows and far ones coarse; with few lights every square grows to use the room. A still point light in the atlas redraws half as often. 24 extra shadowed lamps cost about 0.25 ms a frame (RTX 2060, 1600 × 900). The stats overlay shows how many lights are in the atlas, their square sizes and how full it is. They go by rank (those with Casts shadows, nearest the camera first, among those whose reach it can see; a light keeps its slot while it stays among them, so its cached shadows survive). Each shadowed light costs about 0.5 ms a frame (RTX 2060, 1080p) when its shadows are redrawn. A light that stands still redraws them only every few frames (Scene Settings > Shadows > Update every, default 2 frames; the lights take turns). It redraws at once when it moves, or when something in its reach moves or plays an animation. Trees swaying in the wind do not count, so their lamp shadows update at that rate.
  • Area lights (Inspector > Shape, Create > Tube Light / Rect Light): a Tube is a glowing bar along the entity's local X (Length; Size is its thickness), a Rectangle a panel of Width by Height in local X and Y that shines one way, along local −Z, brightest straight ahead (windows, screens, ceiling panels). Both scale with the entity. Light falls off from the nearest point of the shape, and shiny surfaces reflect the bar or the panel instead of a dot. Their shadows come from the middle, softened by their size. Scripts: e.light.shape = "tube" (or "rect", "sphere"), width, height. Scenes/lights.json has a tube lamp.
  • Light size (Inspector > Size, metres; 0 = a point): a light the size of a glowing ball. Highlights get wider, and shadows are sharp where an object touches the ground and soften the further they fall from it (PCSS). The torches in Scenes/lights.json are 0.15 m.
  • Contact shadows (Scene Settings > Shadows > Contact shadows, the ray's length, default 0.25 m; each light can turn them off): a short ray through the screen's depth from each lit pixel towards the light darkens what shadow maps miss: small things, the gap under an object, and lights that cast no shadows of their own. Up to 2 lights a pixel, nearer than 40 m; about 0.35 ms with a floor lit by 260 lamps. The sun gets them too (Sun contact shadows, on by default; it takes one of the two rays).
  • Casters are culled per shadow view; the stats overlay shows how many were skipped.
  • Settings: shadow distance, cascade split, biases, extent (Scene Settings > Shadows).
  • Cached far cascades (Scene Settings > Shadows, default 2 of 4): the far sun cascades keep their shadows from frame to frame and redraw the still things in them only when the camera has moved well away, the sun turns, or every few frames (Refresh every, default 4: swaying trees). Moving and animated things are drawn on top of a copy each frame, so they never lag. A sun with no light (intensity 0, a night scene) casts no shadows at all. On the village by day the cache saves about 0.35 ms a frame; at night, skipping the dark sun saves about 2 ms.
local lamp = scene.spawn("Lamp", vec3(0, 3, 0))
lamp:add_light{ color = vec3(1, 0.7, 0.4), intensity = 2, shadows = true }
local torch = scene.spawn("Torch", vec3(4, 1, 0)):add_light{ color = vec3(1, 0.5, 0.2), range = 4 }
torch.range = 6          -- metres; 0 = automatic. torch.reach: the range in use

Environment & sky

Ambient light comes from image-based lighting: irradiance and prefiltered cube maps baked from an HDR panorama in Assets/Environments, or a procedural sky when none is loaded. Sky visibility, blur, rotation and ambient intensity are scene settings. Double-clicking an .hdr in the Assets panel makes it the sky.

Post-processing

  • SSAO: radius, bias, samples, strength (Viewport > Debug shows it alone). Computed at half resolution (AO is soft, and that costs a quarter as much) and applied to the opaque scene before the sky, glass, volumetric fog and particles, so fog in front of a corner is not darkened, and before TAA, which smooths its noise (it no longer flickers through fog). Its blur and its upscaling respect depth, so the darkening of a corner does not bleed onto an object in front of it. With the depth pre-pass (the default) it is worked out before the lighting and dims only the light from the sky and the environment, so sunlight and lamps aren't darkened in creases.
  • Bloom: threshold with soft knee, radius, intensity, brightness ceiling (no fireflies).
  • Tone mapping: ACES (default) and others, exposure, gamma.
  • Temporal anti-aliasing (TAA), on by default: every frame is drawn shifted by a different fraction of a pixel (8 positions) and blended with the frames before it, following each surface as it moves. Edges, thin leaves, grass and noisy effects (volumetric fog) stay smooth and steady in motion instead of shimmering. To avoid smearing, the old frames are only allowed colours found around each pixel in the new frame. A thin object moving fast close to the camera can still look slightly soft. Viewport
  • FXAA anti-aliasing.

Batching, instancing & static merging

Objects with the same geometry part, textures and alpha state are drawn as one instanced batch. Skinned meshes are batches of one.

Static merging: Mesh Renderers marked Static that use a unique mesh are merged, when Play starts, into world-space chunks per material and 8 m cell. Repeated meshes stay instanced (that is faster). Moving or recolouring a merged entity during Play is not seen.

local s = scene.render_stats()
ui.text(s.draw_calls .. " draws, " .. s.static_merged .. " merged", 0.02, 0.95)

Levels of detail

A Mesh Renderer can swap in coarser geometry as it gets further away, and stop drawing altogether past a cull distance. Open Inspector > Mesh Renderer > Levels of detail, press + Add level, then pick the level's geometry (a built-in shape or any model under Assets/Models, or drop a model from Assets onto the picker) and the distance it starts at. Cull distance hides the object, and its shadow, beyond that point (0 = never). The level being drawn is marked in the list.

  • Distance is measured from the camera to the middle of the object's box, as if through a 60° lens: a narrower field of view (zooming in) keeps detail further out. Scene Settings > Levels of Detail > Distance scale multiplies every switch and cull distance (2 = detail kept twice as far; saved with the level, scene.lod_scale in scripts, handy as a quality option).
  • Going back to a finer level waits until the object is 5% nearer than the switch distance, so an object standing right at it doesn't flicker between two levels.
  • The camera and every shadow view draw the same level, so an object never shadows itself with a different shape. A cached point-light shadow is redrawn when a nearby caster changes level.
  • A level is drawn in the main geometry's place: it shares the LocalOffset (the fit-to-2-m scaling of a placed model), colour, alpha, wind and the other settings. So make model levels in the same units and pivot as the main model, e.g. exported from the same Blender file. With Use model materials, each level uses its own file's materials. Wind sway uses the main geometry's height, so all levels bend alike.
  • An animated (skinned) model's levels must be skinned with the same bones (same count, same order: one rig, decimated). A level that isn't is skipped and the main model is drawn instead; the Inspector warns.
  • Objects with levels or a cull distance are never merged into static batches (their level is picked every frame). Picking, colliders, grass footprints and bounds use the main geometry.
  • Viewport > Debug > LOD Levels tints objects by level (green = main geometry, then yellow, orange, red, purple). The stats overlay shows how many objects are on a lower level or culled; scripts read scene.render_stats().lod_reduced / lod_culled.

Culling through the camera

The game camera decides what is too small or too far to draw. These settings are in Inspector > Camera:

  • Hide small objects: an object whose bounding sphere would cover less than this share of the view height is not drawn, and neither is its shadow. Small props go first, buildings much later, with no setup per object: the size is the object's bounding box, so at 1% through a 60° lens a 1 m crate hides beyond about 150 m and a 10 m house beyond 1.5 km (2 to 3% suits small props; the Inspector shows the distances for the value you pick). The same 5% hysteresis as levels of detail stops flicker. A zoomed-in lens keeps things further, and Scene Settings > Levels of Detail > Distance scale stretches it like every other distance (a quality option). An object's own Cull distance still applies when it is nearer. A selected object is never hidden this way. During Play, merged static batches are judged as one object each. 0 = off, the default.
  • Grass distance multiplies every grass field's Draw distance through this camera: 0.5 halves it, 0 draws no grass.
  • The editor's own camera culls the same way as the primary game camera, so the Viewport shows what the game will draw. Turn this off with Viewport > Camera > Cull Like the Game Camera.
  • Scripts: e.camera.small_objects (0.01 = 1%), e.camera.grass_distance, and the same keys in add_camera. Culled objects count in the stats overlay's LOD line and in render_stats().lod_culled.
Culling already in the engine: every view (the camera, each point-light cube face, the sun cascades) skips what is outside its frustum, for meshes, static batches, terrain chunks and grass chunks; shadow casters are also skipped beyond a light's reach. There is no occlusion culling: an object hidden behind a wall but inside the view is still drawn. It was measured not to be worth it yet: the depth pre-pass already skips shading hidden pixels, and in the example levels only 0 to 12% of the visible triangles were hidden. To check a level of your own, run it with MDB_OCCLUSION_ORACLE=1: the log says how many parts and triangles a perfect occlusion test would have hidden.

Levels inside one model file

A model file can carry its own levels: name the objects MyTree_LOD0, MyTree_LOD1, MyTree_LOD2 (any case; the usual Blender / Unreal / Unity naming), or give the glTF nodes an extra "lod": n. When you place such a model, drop it on a Mesh Renderer or pick it as Geometry, its levels are filled in for you, at distances worked out from its size (about when it fills 40%, 20%, 10% of the view). A node extra "lod_distance" (metres) sets a level's distance instead. Scripts get them too: add_mesh{ geometry = "model:Models/Trees/Oak.gltf" } fills them in unless you pass lods. In scene files and scripts a level is named model:<file>#lod1, #lod2 …; the LOD picker lists the main file's levels first, and Use the file's levels / Reset distances put them back.

Objects in the file that belong to no level are drawn at every level. A collision mesh (named UCX_… or …_COL, or with a "collision" node extra) is never drawn: Convex hull and Mesh colliders use it instead of the visible mesh, and so do grass footprints. Files without any of these load exactly as before. (Not for animated models: a skinned file is not split into levels.)

The engine does not generate the coarser meshes: make them in your modelling tool (Blender's Decimate modifier, or fewer leaf cards for trees). Levels switch instantly (no cross-fade).

Skeletal animation

Models with bones (glTF/FBX) keep their skeleton and clips; the GPU skins up to 128 bones, 4 weights per vertex.

  • Clips with cross-fade when the clip changes.
  • Clips from other files (a clip library): animations exported on their own (one .glb per set, made for the same rig) join a model through a file beside it named <model name>.clips.json, for example Models/SkeletonRig.clips.json = { "clips": [ "Animations/Walks.glb", "Animations/Idle.glb" ] } (paths in Assets). Their clips are matched to the model's bones by name (channels for bones it doesn't have are left out, with a warning) and appear with its own everywhere (Inspector, graphs, a:clips()); a clip named like one the model already has is skipped, so the model's own and earlier files win. The Console logs how many clips came from how many files.
  • Animation graphs: state machines, 1D and 2D blends, layers and conditions (below).
  • Layers: another clip on a bone and its descendants (mask), override or additive, with fading weights.
  • Events at clip times → on_anim_event, or "sound:Sounds/x.wav" plays a sound.
  • Root motion: the root bone's travel moves the entity.
  • IK: look (head turns towards a target) and limb (two-bone reach), also in Edit mode.
  • Foot placement (Inspector > Animator > Foot placement; Find feet picks bones named foot / ankle / paw): during Play a ray under each foot finds the ground; feet move up or down to it and turn with its slope, and the pelvis drops for the lowest one so downhill legs reach. Keep the entity's origin at the feet. On a character controller it fades out in the air. The terrain demo's Hillside Fox uses it.
self.animator:play("Run", 0.3)
self.animator:set_layer(1, { clip = "Survey", mask = "b_Neck_04", weight = 0, additive = true })
self.animator:layer_weight(1, 1, 0.6)                       -- fade in over 0.6 s
self.animator:set_ik(1, { type = "look", bone = "b_Head_05", target = player, max_angle = 75, chain = 2 })

Animation graphs

An animation graph (Assets/AnimGraphs/<name>.json, made in the AnimGraph Editor) is a set of state machines driven by parameters. Pick it as an Animator's Graph (Inspector) and it makes the pose instead of the Animator's clip; the Animator's own layers, IK, events and root motion still apply on top.

PartWhat it does
ParametersNamed values of type float, int, bool or trigger (a bool that the transition using it resets). Scripts set them (set, trigger); the editor can change them while the game runs.
LayersThe first layer makes the base pose. Each further layer runs its own state machine over its mask (a bone and everything below it), replacing the pose by its weight (optionally times a parameter, so scripts can fade it) or, when additive, adding its motion relative to the state's first frame (a head turn or breathing over any walk).
StatesPlay one clip, or a 1D blend: clips placed along a number parameter (walk at 1.1, run at 3.6). The two clips around the value are blended and share one phase, so feet stay matched; past either end the end clip plays. Or a 2D blend: clips placed on the plane of two parameters (X sideways speed, Y forward speed: idle at 0, walks and runs around it), weighted by gradient band interpolation and sharing one phase the same way. Directional weights (for velocities) work in speed and heading, so between two directions the speed is kept; Cartesian uses plain distances (for parameters that aren't a direction). Beyond the outermost points the nearest clips play. Directional needs the directions to go all the way round (no gap over half a turn, else the blend jumps there: the problems list warns). Each point of a blend (1D or 2D) has a cycle offset (0..1 of its clip, looping states): clips that start on different feet are shifted so the same foot lifts at the same phase; without it, blending two such clips averages the steps into a shuffle. Matching feet to movement: put each walk at its own natural velocity (how fast its planted foot moves) and set a speed parameter to real speed divided by the blended clips' velocity (their positions weighted by blend_weights()); then the feet stay planted in every direction. Cartesian weights follow velocities more closely than Directional when the clips' speeds differ a lot (short side steps against long forward strides). Speed, an optional speed parameter, loop or play once.
TransitionsFrom a state (or from Any State) to another, when all conditions hold (> < == != on numbers, is true / false, a trigger fired) and, with an exit time, once the state has played that share of its length (an exit time alone moves on at the end, like a one-shot attack). The two states cross-fade over its blend time. Any State transitions are checked first and also during a cross-fade; the others wait for it. In a list, the first that can be taken wins.
EventsEntering a state calls on_anim_event(self, "enter", stateName). Clip events fire from the clip that leads a blend.

The example AnimGraphs/fox.json: Idle (Survey), Locomotion (Walk ↔ Run on speed), a one-shot Look reached from Any State by the look_around trigger and left by exit time, and an additive Head layer on b_Neck_04 weighted by head. Scripts/wander_graph.lua drives it.

Graphs are read once and shared; the editor makes every edit live at once for the animators using that file (their states are kept by id). Not saved in scene files or save games: the parameters' values and the current states (a loaded game starts each layer in its entry state; scripts can restore what matters with play_state in on_load).

Particles

CPU-simulated billboard particles. An emitter has a rate, burst, spread cone, shape (point, box…), gravity scale, drag, size and colour over life, emission brightness and optional texture/additive blending. Presets: Fire, Smoke, Sparks, Magic, Dust, Embers. Emitters preview live in Edit mode.

self:add_particles("Fire")
scene.spawn_particles(self.position, { preset = "Sparks", count = 40 })   -- one-shot, removes itself

Decals

Shapes projected down onto whatever is under them — floor, steps, ramps — for target circles, area templates, movement ranges and path markers. Scripts add them every frame (immediate mode, like the UI) into Scene::Decals.

  • Drawn after the opaque scene and the sky, before glass. The renderer copies the depth buffer, draws each decal as a box, rebuilds each pixel's world position and keeps the ones inside.
  • Fade on steep surfaces (walls, step risers) and towards the top and bottom of the box, so rings don't smear up walls.
  • Shapes: circle, ring (an outlined circle), square (grid cells), texture. Outline thickness, inside fill, softness, emission (above 1 glows).
  • Not clickable and not saved; one instanced draw per texture. scene.render_stats().decals counts them.
decal.draw(target, { size = 3, shape = "ring", color = vec3(1, 0.3, 0.2), thickness = 0.08, fill = 0.25 })

Physics

Jolt Physics, during Play only, at a fixed 60 Hz with interpolated transforms.

  • Body types: Static, Dynamic, Kinematic. Any body can be a trigger (sensor).
  • Shapes: Box, Sphere, Capsule (size.x diameter, size.y height), Convex hull, Mesh (static/kinematic), None, Terrain (the entity's terrain as a height field; static/kinematic).
  • Compound colliders: Collider components on children add shapes to the nearest body above them.
  • Events: exactly one begin and one end per touching pair; removed bodies end their contacts.
  • add_force lasts the frame; add_impulse applies once. Moving a static body from a script teleports it.
  • Raycasts (closest, all hits, static only) and sphere casts (scene.spherecast: a ball swept along a ray, for cameras and wide probes). T in the editor throws a ball.
self:add_body{ type = "dynamic", shape = "sphere", size = 0.5, mass = 2, bounciness = 0.6 }
function on_collision_begin(self, other, hit)
    log("hit " .. other.name .. " at " .. tostring(hit.point))
end

Character controller

A Character Controller (Inspector > Add Component, or Create > Character for one with a capsule to look at and its origin at the feet) is for anything that walks: players, NPCs that need real collision. It is an upright capsule moved by Jolt's CharacterVirtual, by sweeps rather than by the solver, so it never tips, bounces or catches on seams. Each fixed step:

  • It walks up steps up to Step height (0.35 m) and slopes up to Max slope (50°). Steeper ground is a wall it slides down.
  • While grounded it keeps to the ground over drops up to Stick down (0.5 m), so walking down a slope or stairs doesn't make it hop.
  • It moves with the ground under it, so it rides moving platforms (kinematic bodies).
  • It pushes dynamic bodies with up to Push strength newtons and presses on what it stands on with its Mass.
  • Gravity (x Gravity scale) is applied for you. The script only gives the wanted sideways velocity and jumps.

It has an inner kinematic capsule, so raycasts hit it (pass it as ignore to skip it), triggers report it (on_trigger_enter) and dynamic bodies bump into it. Collisions with the level itself are not reported as events. A Rigid Body on the same entity is ignored. Its position is the entity's, written back like a dynamic body's (interpolated); setting the position teleports it. Physics never turns it. The collider overlay draws it in teal. Only the settings are saved, not the velocity. village_player.lua is the example; Scripts/character_test.lua checks all of it.

Audio

miniaudio. One-shots (2D or positioned), and one voice per Audio Source that follows its entity (loop, volume, pitch, min/max distance). The listener follows the camera being drawn. Decoded clips are cached; Stop stops all.

Buses. Every sound plays on a mixer bus: sfx (the default), music, voice, ui or ambience, each a miniaudio sound group with its own volume and mute under the master volume (Audio/AudioMix.h). An Audio Source picks its bus in the Inspector (saved as "bus", only when not sfx); one-shots take bus = .... Pause stops every bus except ui, so menu sounds still play. Changing a playing source's bus carries on from the same point.

Volume settings. The game keeps the player's mix in %APPDATA%\<title>\settings.json (with --save-dir: settings.json in that folder; --settings file names it), set in the pause menu's Settings page (a slider and mute for master and each bus) or by scripts, and saved when the player leaves Settings and when the game closes. The editor has its own mix (Scene Settings › Audio, kept in %APPDATA%\MDB Engine\audio.json); during Play scripts may change it, and Stop puts it back.

audio.play("Sounds/coin.wav")
audio.play_at("Sounds/thud.wav", self.position, { volume = 0.8, pitch = 1.2 })
self:add_audio("Sounds/lava_loop.wav", { loop = true, min_distance = 2, max_distance = 14, bus = "ambience" })
audio.play("Sounds/click.wav", { bus = "ui" })

Navigation (NavGrid)

A layered walkability grid baked from static physics bodies. One grid serves both free movement (exploring) and grid movement (turn-based combat).

  • Bake: a ray down every column keeps each upward surface with head room and no wall within the agent radius. A column can hold several cells (ground under a bridge, and the deck).
  • Links to 8 neighbours when the height difference is a step and nothing blocks the way (a thin fence cuts the link). No corner cutting.
  • Free paths: A*, then straightened (any angle), ending exactly at the target.
  • Grid paths: cell centres with step costs (orthogonal 1, diagonal configurable).
  • Blocked cells for units and doors; reachable sets for movement ranges.

Baked lazily on first use (3.8 ms Release for the tactics level). Viewport > View > Navigation Grid draws it during Play. See Scripting › Navigation.

Line of sight & cover

Queries against the static level (the same bodies the nav grid is baked from):

  • Line of sight: a ray from the looker's eyes (1.5 m) to the target's chest (1.0 m). Units don't block it (they have no bodies).
  • Cover at a position against an attacker: three rays across the body (agent radius apart) about a cell towards the attacker. Blocked at waist height (0.6 m) is half cover (crates, fences); blocked at head height (1.5 m) too is full (walls, terraces).
  • Visible cells: every nav cell within a range that a point can see.

Measured on the tactics yard: half behind the crate and the fence, full against the terrace wall, none with the crate behind you. See Scripting › Line of sight.

Fog of war

Three states per nav-grid column: never seen (black), explored (dimmed — you remember the place, not what is there now) and visible (clear).

  • Each frame scripts reveal around their viewers. A column is visible if the viewer has line of sight to chest height there (walls and terraces cast vision shadows; low crates don't). Walls next to a seen floor are shown too.
  • Results are cached per viewer position, so a standing unit costs nothing; a new position costs about 2.5 ms in Debug.
  • Drawn as one fullscreen pass over the scene (from the depth buffer), with soft edges and fades. The sky is left alone and clicks still pick through it.
  • Hide units in the fog with e.visible = false (no shadow either).
  • The explored map is saved by the game (fog.save / fog.load in on_save / on_load).
  • Editor: Viewport › View › Fog of War turns the drawing off while play-testing.

See Scripting › Fog of war.

Game session & play mode

GameSession runs a scene as a game: Start (bodies, then scripts), Update, Stop. Both apps use it.

  • NewGame(level) starts a fresh campaign on the live scene.
  • Loads, level changes and restarts are requested during a frame and done by ApplyPending at the start of the next one.
  • Restart (scene.restart(), the pause menu) enters the current level again as it was entered.
  • The game camera is the primary Camera component (looks along local −Z).

Save games & levels

A level is saved as its differences from its scene file: changed and added entities in full, removed ones by ID. Saves are small (a few KB).

  • Transient entities (markers, particle bursts) are never saved.
  • Scripts save their variables with on_save / on_load.
  • game (campaign data) is kept across levels and saved; shared is per level.
  • Level changes keep the level you leave exactly as left; returning restores it. Entities can be carried along.
  • A save slot holds the current level, every visited level, game and play time; written safely (temp file, then rename).
  • Save folders: the game uses %APPDATA%\<title>\Saves (or --save-dir); the editor uses %APPDATA%\MDB Engine\Editor Saves (or MDB_SAVE_DIR).

Not saved: physics velocities, live particles, the nav grid, Lua locals without on_save. See Scripting › Save games.

Events, data files & Lua libraries

  • Event bus: events.emit(name, data) reaches every script's on_event after the frame's on_update (events emitted inside handlers are delivered in the same pass, up to 8 rounds).
  • Data files: data.load(path) reads any JSON under Assets as a Lua table.
  • Libraries: every Assets/Scripts/Lib/*.lua runs once in the shared globals when scripts start (the dialogue runner lives there).

Script UI rendering

Scripts produce a list of UI items each frame; the app draws them over the view with ImGui's draw list. Two layers build that list:

  • Positioned UI (ui.text/rect/bar/image/button with 0..1 coordinates).
  • Laid-out UI (UILayout): panels, rows, columns and scroll regions place widgets automatically. Sizes are in units (pixels at 720p), so the UI scales with resolution.

Item kinds: text (bold or regular font, optional shadow), rect, border, image (optionally 9-slice), button, clip push/pop. Fonts are Segoe UI Bold and Regular at 64 px.

Build Game (shipping)

File › Build Game… makes a folder you can zip and ship. Set the title, start scene, window size, full screen, VSync and files to leave out (saved to project.json), pick the output folder, press Build.

  1. Compiles Game.exe in Release (the first time takes a few minutes; the editor keeps working, the log shows progress).
  2. Fills <output>/<title>/ with <title>.exe, EngineAssets/, your Assets/ (minus exclude) and project.json.

Play it runs the result and Show in Explorer opens the folder. The game uses the saved scene files, so save first. Players need the Microsoft Visual C++ Redistributable (x64), which most PCs have. A rebuild replaces the earlier build (only a folder that holds a project.json is ever replaced).

Web (browser)

Set Platform to Web (browser) to build a game that runs in a browser (WebGL2: Chrome, Edge, Firefox, Safari). The result is <output>/<title> (Web)/:

game.pakThe same files a Windows build has (EngineAssets, Assets minus exclude, project.json) in one package.

To share it, upload the folder to any web host. On itch.io: zip the folder's contents, upload them as an HTML project. Saves and the player's settings are kept by the browser (IndexedDB, per site). F11 asks the browser for full screen.

The web player comes from Tools/build_web.ps1 (Emscripten 3.1.74 in D:\emsdk, C:\emsdk, %USERPROFILE%\emsdk or MDB_EMSDK; the first build compiles the engine for the web, several minutes). A packaged editor ships it prebuilt in Player/Web.

What differs on the web (a browser shader may use 16 textures, has no compute shaders or storage buffers, and runs on one thread):

  • Point and spot lights cast no shadows (the sun does, with its cascades); no light cookies or IES profiles; no contact shadows.
  • Terrain layers use their colour textures only (no normal / roughness / height maps). Ambient occlusion is applied after lighting.
  • Shader-graph materials can use at most 5 textures.
  • Physics and grass scattering run on one thread. The first start compiles shaders for a few seconds (browsers cache them afterwards).
  • Esc in browser full screen leaves full screen first.
  • The browser must use the graphics card. With hardware acceleration off (a browser setting: "Use graphics acceleration when available"), WebGL is drawn on the CPU: Coin Rush ran at 4 FPS that way against 144 with it on (RTX 2060). The page notices this and shows the player how to fix it.

Game database: items, NPCs, stats

The design data of a game lives in one file, Assets/Data/database.json, edited in the editor's Database window and read by scripts through db and e.npc. It holds:

PartWhat it says
StatsWhat every NPC has (health, attack, armour...): a default, a range, and optionally a ceiling stat (health can't pass max_health). One stat is the death stat (health): an NPC dies when it reaches its minimum.
ItemsName, description (UI markup), kind, equipment slot, icon, model (how it looks lying on the ground), value, stacking, consumable, its own numbers (damage_min...) and effects.
NPCsName, description, model and height, animation graph, script, dialogue, a capsule body, its stats (overriding the defaults), whether its body stays when it dies, a death event, and its starting inventory: items with a count, a chance, whether they drop when it dies, whether they start equipped.

Effects of an item happen on use (npc:use; a consumable is used up), while equipped, or on hit (npc:apply(item, "hit") on what a weapon hits). Kinds: add (at once: a heal, damage), modifier (+amount while it lasts: for some seconds, for good, or while equipped), over time (amount per second: poison, regeneration), event (a script event: events.emit(name, { entity, item, amount })).

NPCs in a scene are entities with an NPC component (just the database id in the scene file). When the game runs each comes to life: its stats from the database and its inventory rolled from the starting one (each chance once). From then on that state belongs to the entity: health, inventory, running effects and whether it is dead are saved with the level (save games, level changes). A stat's value is its base plus running modifiers plus the modifiers of equipped items, kept in its range.

Death: what it carries with drop falls to the ground in a ring round it as pickups (entities with an Item Pickup component: the item's model, or a small gold box, turning slowly). Every script gets on_event(self, "npc_died", { entity, npc, position, drops }) (and the NPC's own death event), then the entity is removed, unless the NPC keeps its body. Picking things up is the game's job (scene.pickups(pos, radius), give it, destroy it), as inventory.lua does.

The file is re-read when it changes, and the editor's unsaved edits apply at once, also while playing. The tactics example uses it: the goblins and the Sage are NPCs of the database, the inventory's items come from it, and on the hero's turn in combat clicking a goblin next to it attacks it with the equipped weapon's damage less the goblin's armour; a dead goblin drops its gold and loot, and walking over it picks it up.

Known limitations

  • Only the first sun is used. Point and spot lights are unlimited (up to 4096), but at most 4 + 64 lights cast shadows at a time (all from the shadow atlas; 4 + 24 by default). Contact shadows fill in small gaps for 2 lights a pixel. Lights can be spheres, tubes or rectangles; area lights shadow from their centre (softened by their size), and shader-graph materials light them as points. Cookies (images, flipbooks) and IES profiles work on any light; a profile shapes the light but does not set its brightness, and a cookie image edited while in use keeps its old copy.
  • Transparency is sorted per entity, not per triangle; glass boxes show front faces only.
  • SSAO darkens direct light too when the depth pre-pass is off (then it is multiplied in afterwards).
  • Animation: no nested graphs (blend trees) or Delaunay-style 2D blending, no full-body IK; graph states are not kept in save games.
  • Compound bodies don't rebuild when parts move during Play; Inspector body changes apply on the next Play.
  • Navigation bakes once, single-threaded, from static bodies only.
  • Terrain: level of detail without blending between levels (a chunk changes level in one step, within the error), one material blend of 4 layers (no per-layer normal maps), no holes; scripts can read it but not sculpt it.
  • Saves: no thumbnails or file versioning.
  • UI: no keyboard/gamepad focus, no text input, Latin glyphs only.
  • Dialogue: no voice, portraits or localization; Lua errors appear at run time.

Shading modes (the Shading menu, the Wire / Solid / Textured / Rendered buttons on the right of the Viewport's menu bar, or keys 1–4). They are an editor view and are not saved with the scene. Looking through the game camera always shows Rendered.

  • Wireframe: every triangle's edges on a dark background, with hidden edges removed. X-ray (Shading menu, or 1 again) also shows the edges behind surfaces. Clicking picks the surface under the mouse, not only the lines. Grass is not drawn.
  • Solid: object colours without textures, under a simple light that follows the camera. Cutout textures (leaves, fences) still cut.
  • Textured: the same light with the albedo textures.
  • Rendered: the full picture (lights, shadows, sky, fog, post-processing).

Solid and Textured skip shadows, the sky, volumetric fog, fog of war, bloom and colour grading. That makes a busy level such as the village much easier to read, and the frame is cheaper. Ambient occlusion stays on if the scene has it.

Selection outline: the selected entity and all of its children get an orange outline. Parts hidden behind other objects get a dimmer outline and a faint orange fill, so you can find a selected object behind walls or trees. View › Selection Outline turns it off.

Viewport menus: View (Grid, Axis Gizmo, Stats, Colliders (off by default), Camera Frustums, Light Gizmos, Navigation Grid, Fog of War, Selection Outline), Shading, Debug (Ambient Occlusion Only, Shadow Cascades, LOD Levels, Light Clusters, GPU Light Binning, Motion Vectors), Camera (Frame Selected, orbit speed). Colliders draw as outlines (triggers in magenta); mesh and convex-hull colliders show their full wireframe only when selected and a bounding box otherwise, so levels built from many mesh-collider pieces stay fast to edit. Cameras draw as frustums. Lights have no mesh and are never rendered: a sun shows as a ring of parallel arrows pointing the way its light travels, a point light as a lightbulb in its colour (a spot light also shows its cone), both the same size on screen at any distance; click them (or box-select) to select them. Older scenes' glowing marker cubes on lights are removed when they load. The grid lies on the ground plane (y = 0): 1 m lines close by, 10 m and 100 m lines further out (each fades in when its squares are big enough on screen), the X axis in red and the Z axis in blue; objects hide it, and it is never in the game. The axis gizmo in the lower left corner shows the world axes as the camera sees them (X red, Y green, Z blue, labelled balls on the positive ends); click a ball to look along that axis around the orbit pivot (X gives the view from the right, Y from above).

Selecting several objects

  • Viewport: a click selects one object. Ctrl+click or Shift+click adds an object to the selection, or removes it if it is already selected. Drag on the scene draws a selection box. It selects every object with a visible pixel inside the box; with Ctrl or Shift held, they are added to the selection.
  • Hierarchy: Ctrl+click adds or removes a row, and Shift+click selects every row between the last clicked row and this one. A plain click on a row that is already selected keeps the whole selection while you drag it, so you can drop all of it onto a new parent at once.
  • The last object you picked is the active one. The Inspector shows it (with "N objects selected" above), and the gizmo sits on it. The gizmo moves, rotates and scales every selected object around the active one's pivot.
  • Delete, Duplicate (Ctrl+D), Unparent and the Hierarchy's right-click menu act on the whole selection. When a selected object is inside another selected object, it moves with its parent and is only handled once.
  • Group (Ctrl+G, Edit menu or right-click): puts the selection under a new empty entity "Group", placed at the middle of their positions. If they all share a parent, the Group goes under that parent. Select All is Ctrl+A.
  • Every selected object is outlined. Where selected objects touch, a thin line divides them.

Hierarchy panel

Undo & redo

Every scene edit is undoable without per-feature code: after each interaction the editor compares the scene with the last state and stores a new whole-scene snapshot if anything changed (up to 100). A whole drag or a typed name is one step, labelled like "Move Player" or "Delete Lava".

Ctrl+Z undo, Ctrl+Y or Ctrl+Shift+Z redo (Edit mode only). Scene settings and the editor camera are not tracked. Quitting or loading with unsaved changes asks first.

Play mode

  • Ctrl+P or the toolbar starts Play: the scene is snapshotted and physics, scripts, animation and audio run.
  • Pause and Step One Frame; Stop restores the snapshot (changes are discarded).
  • Play Through Game Camera: the viewport shows the primary Camera entity. Gizmos, picking and editor shortcuts are off then (except Esc, Ctrl+P, F1, F5), so games can use those keys.
  • F5 reloads shaders, and scripts too while playing.
  • Esc stops Play; in Edit mode it quits (asking about unsaved changes).
  • Level changes during Play bring their own render settings; Stop puts yours back.

Scatter brush

The terrain's Scatter tool paints instances of models and prefabs onto the ground. Each instance is an ordinary entity (select, move or delete any one of them) inside a top-level group entity; moving the group moves them all. A stroke is one undo step.

  • Items: drop models or prefabs from the Assets panel on + Item (or pick from the list). Each has a weight (how often it is picked against the others) and its own scale. Models arrive 2 m tall like a dropped model (kit pieces at their own size), so give a big tree a scale of 4 or so.
  • Group: the name of the group entity. Erasing, Re-snap and Clear touch only this group, so keep trees and rocks in two groups to edit them apart. The number beside it is how many it holds.
  • Density (per 100 m²) is how full the brush gets: painting over a full spot adds nothing. Spacing is the least distance between two instances of the group.
  • Scale range, Random turn about the up axis, lean with slope (0 upright, for trees; 1 tilted to the ground, for rocks), Sink (how far into the ground, so no gap shows on slopes).
  • Rules: Max slope, a Height range, and a paint layer (only where that layer is painted at least so much: trees on grass, not on rock).
  • Instances: Static (on by default: merged in Play, and the grass clears around the trunk), Wind (sway; 0 keeps the item's own), Collider: As made (a prefab keeps its body; kit pieces get a mesh body), None, Trunk box (a static box of the given width and height at the base, default) or Mesh.
  • Fill terrain scatters over the whole terrain by the same rules (with its Seed). Re-snap to ground stands every instance of the group on the ground again after sculpting (keeps turn and lean). Clear group deletes the group.

The settings belong to the editor session and are not saved with the scene.

UI Editor

Window > UI Editor (or double-click a file in Assets/UI) designs game UI as layouts: files in Assets/UI/<name>.json that a script draws every frame with ui.show. A layout is a tree of the same widgets scripts place with ui.begin_panel and friends, drawn by the same layout code, so the preview is exactly what the game shows.

  • Left: the widget tree. Panels sit at the top. Inside them go rows, columns and scroll regions, which hold labels, buttons, text fields, images, bars, slots, spaces and separators. Drag a row onto a container to put it inside, or onto another row to put it before that row. The problems list underneath catches widgets outside a panel, empty containers, buttons nothing can detect, repeated names and missing images.

    • Zoom and pan: the wheel zooms around the pointer (Ctrl+wheel while trying it, where the wheel scrolls the UI), right or middle drag pans, F (or Frame) zooms onto the selected widget, Home (or Fit) shows the whole view again.
    • Expressions are worked out on the layout's Preview data: sample values written as JSON, such as { "game": { "gold": 120 }, "hp": 7 }. Texts, bars, counts, conditions and repeats then show realistic content. Any expression that fails on those values is listed under the preview.
    • Try it makes the pointer work the layout as in the game. Buttons light up and click, and their on_click runs on the preview values, so a button that sets open = false really hides its panel. Reset values puts the values back.
  • Right: the selected widget's properties.
    • Panels: title, position, anchor, size, padding, close button, colour and alpha, a 9-slice frame image.
    • Labels: text with markup, size, colour, alignment, bold, muted, wrap.
    • Buttons: text, on click, event, disabled, selected, size, fill.

Video settings and player options

For a game's own options menu. video.* reaches the player's display and quality settings (Core/VideoSettings.h): the Game applies them to the window and the renderer at once and keeps them in the video key of the player's settings.json (written a second after the last change, and on quit). F11 / Alt+Enter change the same full screen setting. The project's fullscreen / vsync are only the defaults; --fullscreen, --windowed and --no-vsync win over the saved choice for that run. The quality switches only turn off what a level has on (a level without volumetric fog stays without it), and brightness multiplies the level's exposure. The editor has no video settings: there video.available() is false, video.get() is nil and video.set does nothing.

prefs.* keeps a game's own options (gameplay switches, camera speed) across runs in the prefs key of the same file, written at once. Values are booleans, numbers or strings. Without a settings file (the editor) they last until the editor closes.

if video.available() then
    local v = video.get()     -- { fullscreen, vsync, shadows, ambient_occlusion, bloom, volumetric_fog,
                              --   antialiasing = "off"|"fxaa"|"taa", brightness = 0.5..2 }
    video.set("fullscreen", not v.fullscreen)
    video.set("antialiasing", "fxaa")
    video.set("brightness", 1.2)
end

local speed = prefs.get("pan_speed", 1)   -- the stored value, else the default
prefs.set("pan_speed", 1.5)               -- nil removes it

A wrong key or a wrong type of value is a script error. With audio.set_volume and input.set_bindings (also kept in settings.json), a script can build a complete options menu of Video, Audio, Input and Game pages.

Sources: key:<name> (A–Z, 0–9, F1–F12, Space, Enter, Escape, Tab, Backspace, Up/Down/Left/Right, LeftShift, LeftCtrl, LeftAlt, RightShift, RightCtrl, RightAlt, Insert, Delete, Home, End, PageUp, PageDown, punctuation by name, KP0–KP9), mouse:Left|Right|Middle, pad:<button> (A B X Y LB RB Back Start Guide LS RS DPadUp DPadDown DPadLeft DPadRight) and stick or trigger halves pad:LeftUp / LeftDown / LeftLeft / LeftRight (and Right…), pad:LT, pad:RT. A vector's bindings take the groups key:WASD, key:Arrows, pad:LeftStick, pad:RightStick, pad:DPad.

Values: a button is its strongest source; an axis is positive minus negative; a vector is (right − left, up − down), shortened to length 1 so diagonals on keys are not faster. An action is down at strength 0.5 and stays down until it falls below 0.35 (a trigger held near the middle doesn't flicker). Sticks have a radial dead zone (deadzone, rescaled so just outside it is 0), triggers a plain one. input.actions(), input.action_type(name) and input.bindings(name) list them (for prompts or a controls screen). An unknown action, button or axis name is a script error that lists the names there are.

Gamepads are anything GLFW has a gamepad mapping for (XInput pads, most known controllers), in an Xbox layout. The active pad is the one used last: another pad takes over when it presses a button, and plugging and unplugging are logged. In the game, Start opens and closes the pause menu and B backs out of it. Tests use input.simulate_key(Key.W, true) and input.simulate_gamepad({ A = true, LeftX = 0.7 }) (values before dead zones; nil gives the real pad back); Scripts/input_test.lua checks it all (28 checks).

Rebinding. Players change bindings in the game's pause menu, Settings › Controls: one row per action (and per direction of an axis or vector), a Keyboard / mouse cell and a Gamepad cell. Choosing a cell waits for the next key, mouse button, pad button or stick / trigger push, which replaces that device's bindings for that row (Esc or Start cancels, Delete or the pad's Back clears it); a note says when the new key also drives another action. Reset to defaults goes back to input.json. The player's bindings are overrides on top of the file, saved in the input key of the same settings.json as the volumes, so an update to the game's input.json still reaches every row the player didn't change. In input.json, an action in the object form may add "label": "Talk / use" (the menu's name for it; else the name with a capital, move_left → "Move left") and "rebind": false to leave it out of the menu (the ui_* actions are left out unless they say "rebind": true). Rows follow the file's order.

Text fields

ui.input is a one-line text field. Keep the text it returns and pass it back the next frame. A click, Tab / Shift+Tab, or focus turning true gives it the keyboard. It has a caret and selection (drag, Shift+arrows, Ctrl+A), Ctrl+arrows and Ctrl+Backspace by word, and Ctrl+C / X / V. Enter submits (and lets go, unless keep_focus); Escape puts back the text it had when it was focused. A click anywhere else, or not drawing the field, lets go too.

local submitted
name, submitted = ui.input("name", name, { hint = "Your name", max = 16, filter = "name" })   -- filter: integer, decimal, name
if submitted then start_game(name) end
code = ui.input("pin", code, { password = true, filter = "integer", max = 4, w = 120 })
-- a chat line: Enter sends and keeps typing; clearing the text you pass in is taken over by the field
local send
chat, send = ui.input("chat", chat, { keep_focus = true, hint = "Say something" })
if send and chat ~= "" then say(chat); chat = "" end
if ui.typing() then return end   -- a field has the keyboard (game keys and input actions read as up meanwhile)

While a field has the keyboard, the game sees no keys: input actions and input.key_* read as up (typing "c" doesn't start combat), keys still held when it lets go stay up until released, and the Game's Esc (pause) and the editor's Esc (stop) leave it alone. In the editor, typing reaches the game while the Viewport has focus and you look through the game camera. Gamepad and keyboard navigation

Laid-out UI can be worked without a mouse. Buttons, slots, text fields and sliders take the navigation focus, drawn as a ring:

  • The arrow keys, the D-pad or the left stick move it to the nearest widget that way (in its own panel first; held, they repeat). Tab / Shift+Tab go in draw order.
  • Enter or the pad's A presses it. On a text field it starts typing (the pad's A then submits and B cancels). On a slot with drag it picks the item up; the next slot you confirm gets it as dropped (Back puts it back).
  • The pad's X right-clicks a slot (use a potion). Left / Right change a slider.
  • Escape or the pad's B is Back: it closes the focused panel if it has close = true, else the topmost one that has; with none, ui.back() returns true once. While a closable panel is up, Esc is the UI's (the Game doesn't pause, the editor doesn't stop Play; the pad's Start still pauses).
  • The first press only shows where the focus is. The ring hides when the mouse moves, and the focus follows the pointer, so you can switch at any time. When the pad was used last, the ring shows at once.
  • A panel that appears (a dialogue, the inventory) takes the focus: its widget with default_focus = true, else its first. When the focused widget goes away, the focus goes back to a default.
  • Disabled buttons can take the focus (to read their tooltip) but not be pressed. Tooltips show for the focused widget too, and a slot reports hovered while it has the focus.
if ui.button("New game", { default_focus = true }) then ... end
if ui.nav_focused() then show_details(item) end   -- the widget just placed has the focus
if ui.back() then menu_open = false end           -- Back, with no closable panel to close
if ui.navigating() then ... end                   -- the ring is showing (Enter / A belong to the menu)
ui.focus_default()                                 -- move the focus to the default again

The keys and buttons are the input actions ui_up, ui_down, ui_left, ui_right, ui_confirm, ui_back and ui_secondary. They exist by default (arrows, Enter, Escape; D-pad, left stick, A, B, X); define any of them in input.json to bind it yourself. They are input actions like any other, so a game's own action on the same button (jump on A) still fires: check ui.navigating() if that matters. In tests, drive it with input.simulate_key(Key.Down, true) or input.simulate_gamepad{ DPadDown = true }. The Game's pause menu and Settings page are built the same way, and work with the mouse, the arrows + Enter or a pad.

UI: layouts from the UI Editor

A layout made in the UI Editor is drawn with one call each frame, in place of the ui.begin_panel ... ui.end_panel code it stands for. It returns the name of the button or slot clicked this frame (or of the panel whose x was clicked), plus its repeat index.

function on_update(self, dt)
    local clicked, index = ui.show("UI/pause.json", { vars = { score = score } })
    if clicked == "resume" then paused = false end
    if clicked == "slot" then use_item(index) end
end
  • Where values come from. Text takes markup and {=expr}, for example Gold: {=game.gold}. Numbers and switches can be expressions, such as a bar's hp / max_hp or a button's disabled game.gold < 10.
    • Expressions run in the calling script's environment, so they see its globals and the shared ones (game, shared, db ...).
    • A script's local variables are invisible to them. Pass those in vars, which take priority over the script's own names.
    • on_click and on_close are Lua statements. Their assignments go to the script, so open = false sets the script's own open.
  • Conditions and repeats.
    • visible hides a widget and everything inside it while the condition is false or nil.
    • repeat draws a widget once per entry of a count or list, with index and item set for its expressions. For example, a row of slots with repeat game.bag can use the icon {=item.icon}.
  • Events. A widget's event sends events.emit(name, { ui = path, widget = name, index }).
  • Errors. A broken expression is reported once in the Console, its text shows ?, and the rest of the layout still draws.
  • Options. id keeps two copies of one layout apart. The default is the path.

Example: the tactics HUD (UI/tactics_hud.json, drawn by tactics.lua with its locals passed as vars), and the goblin card shown while the pointer is over a goblin (UI/target.json), whose loot row repeats one slot per item carried. The file format is described in Runtime/UIDocument.h.

Dialogues are made in the Dialogue Editor. Play one from any script:

function on_update(self, dt)
    if not talk and input.key_pressed(Key.T) then
        talk = dialogue.open("sage", { speaker = self })      -- Dialogues/sage.json

Inside a dialogue

  • Conditions are Lua expressions: game.gold >= 25, has_item("gem"), not game.met_sage.
  • Actions are Lua statements: game.gold = game.gold - 25; give("potion").
  • They see the globals, speaker (the entity talking) and every function in dialogue.helpers.
  • Text takes UI markup and {=expr}: You have {=game.gold or 0} gold.
  • Events go to every script's on_event with { dialogue, node, speaker }; the runner also sends dialogue_started and dialogue_ended.
-- add your own helpers for dialogue code
dialogue.helpers.reputation = function(faction) return (game.rep or {})[faction] or 0 end

-- react to a dialogue event
function on_event(self, name, data)
    if name == "magic" and data.speaker == self then scene.spawn_particles(self.position, "Magic") end
end
